# 12. Outbox、Kafka、Inbox、DLQ：异步一致性核心

## 本章定位

文件上传完成后，系统需要异步扫描。难点是：业务 DB 已提交后不能丢扫描事件；Kafka 事件重复到达时不能重复产生副作用；扫描一直失败时要留下可恢复证据。当前实现用 Outbox、Kafka、Inbox、DLQ 组合解决这个问题。

总链路：`upsertFileAndRelation 写 Outbox -> OutboxDispatcher 投递 Kafka -> store_srv consumer -> tryBeginInbox 幂等 -> scan/finalize -> failed/retry/DLQ`。

与"上传请求里直接调 Kafka"相比，这个链路多了一张 DB 表（Outbox）和两个后台组件（dispatcher、DLQ consumer）。理解本章的关键是三个"为什么"：为什么不在上传请求里同步发 Kafka（要保证 DB 与消息同事务，即 outbox 模式）；为什么消费端还要一张 Inbox 表（Kafka 只能做到至少一次投递，重复要靠业务侧去重）；为什么还有 DLQ（重试必须可控，不能把主队列无限堵住）。

代码证据：`backword_part/model/filedb.go:40-51`

```go

	OutboxSending OutboxStatus = "SENDING"
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
```

解释：

- `OutboxStatus` 的四个状态就是 dispatcher 状态机的全部状态：NEW 待发送、SENDING 已抢占正在发送、SENT 已确认送达、FAILED 失败待退避重试。
- `FileUploadEventTopic = "file.upload.cmd"` 是主题命名约定：`<业务>.<动作>.cmd`，命令型事件；DLQ 主题是主主题加 `.dlq` 后缀（见第 13 章 main.go），即 `file.upload.cmd.dlq`。

## 源码精读：Outbox 是 producer 侧一致性边界

Outbox 表是 DB 与 Kafka 之间的一致性边界。上传接口在业务事务里创建 Outbox 行，事务提交后 dispatcher 才把行变成 Kafka 消息。这样"文件/用户文件落库"与"产生扫描事件"要么一起成功、要么一起失败，不会出现"DB 有文件但 Kafka 没消息"的丢事件窗口。

代码证据：`backword_part/model/filedb.go:74-90`

```go
type Outbox struct {
	gorm.Model
	EventID     string       `gorm:"type:varchar(64);not null;uniqueIndex:uk_event_id;comment:事件唯一ID（幂等键）"`
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `EventID` 带唯一索引，是幂等键：它随 payload 一起进 Kafka，消费端 Inbox 用它去重（见下文 Inbox 节）。
- `Topic/Key/Payload/Headers` 四个字段直接对应一条 Kafka ProducerMessage：Topic 是 `file.upload.cmd`，Key 用文件 hash，保证同一文件的事件落在同一分区、顺序消费。
- `Status/RetryCount/NextRetryAt/LastError` 是 dispatcher 的重试状态：发送失败后按指数退避更新 NextRetryAt，dispatcher 到点再次捞取。
- `LockedBy/LockedUntil` 是多实例抢占锁：谁抢到就把锁写给自己，租约期内其他实例跳过该行（见 claimBatch 节）。

## 源码精读：Dispatcher 轮询并分发 worker

OutboxDispatcher 是 file_srv 内的后台组件，main 启动时 `go dispatcher.Start(ctx)` 常驻运行。它由两部分组成：一个 poller 每隔 2 秒查一次 outbox 表，8 个 worker goroutine 并发执行真正的 Kafka 发送。Kafka 投递不在上传请求里同步完成——上传请求只负责写 outbox 行、返回客户端；发送是后台补偿动作。

代码证据：`backword_part/file_server/file_srv/kafkaproduct.go:19-42`

```go
type OutboxDispatcher struct {
	db           *gorm.DB
	producer     sarama.SyncProducer
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `instanceID = hostname-pid`：多实例部署时每个 dispatcher 有唯一身份，写进 Outbox.LockedBy，避免 A 实例释放 B 实例的锁。
- 四个调参点：pollInterval 轮询间隔 2s、batchSize 每批最多抢 50 条、workerCount 8 个并发发送 goroutine、lockTTL 抢占锁租约 30s。
- `producer` 是 sarama SyncProducer（`internal.KafkaProducer` 全局单例，见第 06 章）：同步发送、等待 broker ack，保证"先发成功、再改 DB"的顺序。

代码证据：`backword_part/file_server/file_srv/kafkaproduct.go:45-86`

```go

// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
```

解释：

- 生产者-消费者模型：poller 是 producer，把 claim 到的 Outbox 塞进带缓冲的 `jobs` channel（容量 batchSize*2）；worker 是 consumer，从 channel 取一条发一条。
- 优雅退出：`ctx.Done()` 时 close(jobs) 并 wg.Wait() 等全部 worker 收尾，进程重启不丢已抢占的消息（SENDING 行重启后仍可被标记失败/重试，见下节说明）。
- 每轮 tick 只 claim 一次；worker 空闲时阻塞在 channel 上等待，不会空转。

代码证据：`backword_part/file_server/file_srv/main.go:84-87`（dispatcher 启动位置）

```go

	dispatcher := NewOutboxDispatcher(internal.DB, internal.KafkaProducer)
	go dispatcher.Start(ctx)
	internal.Logger.Info("kafka producer is running")
```

解释：

- dispatcher 与 gRPC 服务同进程：上传 RPC 写 outbox，同一进程的 dispatcher 把它发出去。
- 即使这个进程崩溃，outbox 行还在 DB 里（NEW 或 SENDING）；重启后或另一个实例的 dispatcher 会继续投递——这是 outbox 模式相对内存队列的最大优势：进程死亡不丢事件。

## 源码精读：claimBatch 用 DB 锁支持多实例

claimBatch 是 dispatcher 的抢占逻辑：找出所有可发送（NEW/FAILED 且已到退避时间、锁已过期）的记录，用 `FOR UPDATE SKIP LOCKED` 锁定，并在同一事务里批量置为 SENDING。SKIP LOCKED 是关键：多个 file_srv 实例同时跑 dispatcher 时，每行只被一个实例锁住，其他实例直接跳过该行而不是阻塞等待，从而让 outbox dispatcher 可以横向扩展。

解释：

- WHERE 条件三层过滤：`status IN (NEW, FAILED)` 只抢可发送行；`next_retry_at <= now` 尊重退避时间；`(locked_until IS NULL OR locked_until < now)` 只抢从未被锁或锁已过期的行。
- `SELECT ... FOR UPDATE SKIP LOCKED` 与"UPDATE 置 SENDING"在同一个事务里完成，"抢占"与"上锁"原子生效，另一实例的 SELECT 在同一行上要么拿到锁要么直接跳过。
- 锁租约 30s 只保护"正在发送中"的行不被并发抢走；`markSent/markFailed` 的 WHERE 还带 `locked_by = d.instanceID`，只有锁持有者能推进状态（见下节）。
- 已知边界：如果实例在 markSent/markFailed 之前崩溃，记录会停留在 SENDING，而 claimBatch 只捞 NEW/FAILED，没有把超时 SENDING 拉回 NEW 的恢复逻辑——outbox 保证"进程死亡不丢 NEW 事件"，但 SENDING 崩溃窗口需要人工/运维介入。这也是阅读检查的重点之一。

代码证据：`backword_part/file_server/file_srv/kafkaproduct.go:197-237`（markSent、markFailed、backoff）

## 源码精读：Kafka send 成功后无法靠 DB 回滚

sendOne 把 Outbox 行变成真正的 Kafka 消息。这里的失败模型决定了整个系统的边界：Kafka send 与 DB markSent 是两次独立操作，不可能原子。如果 Kafka 已收到消息但 markSent 失败，outbox 未来可能再次发送同一 event（重复）；如果 Kafka 没收到但 markFailed 也失败，消息会滞留在 SENDING。既然 producer 侧无法保证 exactly-once，consumer 侧就必须幂等——这就是 Inbox 存在的原因。

## 源码精读：Inbox 是 consumer 侧幂等门禁

Inbox 表是消费端的"处理登记表"，主键就是 event_id。消费者处理一条消息前先 tryBeginInbox：能插入记录 = 第一次处理，拿到独占权；记录已 DONE = 直接跳过；记录被其他实例 PROCESSING = 放弃（等退避后重试）；记录 DLQ = 默认跳过，只有 DLQ 消费者重放时允许再处理。这样即使 Kafka 重复投递、多个 consumer 同时抢同一事件，最终副作用也只执行一次。

代码证据：`backword_part/model/filedb.go:92-111`


- `EventID` 是主键：唯一索引让并发 INSERT 只有一个成功（另一个撞 Duplicate entry），这是幂等抢占的根基。

## 源码精读：DLQ 是失败可恢复证据

当一条消息耗尽重试次数仍失败（或错误不可重试）时，它进入死信链路：Kafka 侧投递到 `file.upload.cmd.dlq` topic，MySQL 侧落一条 dlq_failures 记录，Inbox 标记为 DLQ。DLQ 不是成功路径，也不是简单日志：它保存"哪个事件、什么 payload、失败原因、尝试次数"，并由低频率的 DLQ 消费者负责重放和收敛。

- 同一事务里做两件事：创建 DLQFailure（status=pending）＋ 把对应 Inbox 置为 DLQ 并写入 `dlq_failure_id` 关联。DLQ 记录或 Inbox 标记要么一起成功、要么一起回滚。
- Inbox 置 DLQ 同时释放锁（locked_by 清空、locked_until 置空），意味着该事件进入"由 DLQ 链路接管"的状态，普通主消费者不再碰它（tryBeginInbox 的 allowDLQRetry=false 分支）。
- 注意与第 12 章 outbox 侧不同：这里 Inbox 更新失败只记 Warn 不返回错误——DLQ 记录已创建是优先保证的，Inbox 标记允许事后通过 dlq_failure_id 对账。

- 未收敛才把状态置为 retrying，并用 `OriginalValue` 重建 sarama.ConsumerMessage，交给主消费者的 `processDLQMessage` 重新处理（allowDLQRetry=true，Inbox 从 DLQ 拉回 PROCESSING）。
- 重放成功 → markResolved（"Auto-recovered by DLQ consumer"）并同步把 Inbox 置 DONE；重放失败 → FailureCount+1，超过 DLQ MaxRetries（默认 1，见 dlq_consumer.go:23-29）则 markFailed 并告警，否则回到 pending 等下一轮（5 分钟一次轮询）。
- DLQ 消费者是低频恢复器而不是高吞吐消费者：它不阻塞主队列，也不追求即时重放，符合"死信是例外路径"的定位。

## 状态转换

Outbox、Inbox、DLQ 是三套状态机，分别覆盖生产端、消费端和失败恢复端。

```text
Outbox: new -> sending -> sent
Outbox: new/failed -> sending -> failed -> next_retry_at 到期后再次 sending
```

```text
Inbox: absent -> processing/locked -> done
Inbox: processing -> failed/expired lock -> retry/reacquire
Inbox: done -> duplicate event arrived -> skip
```

```text
DLQ: terminal failure -> dlq pending -> retry/replay -> resolved 或继续 failed
```

关键结论：系统是“至少一次投递 + consumer 幂等 + DLQ 可恢复”，不是 exactly once。Kafka send 成功但 `markSent` 失败时，重复消息是允许发生的；`tryBeginInbox(event_id)` 才是防重复副作用的核心。

## 关键数据结构 / 字段

- `Outbox.event_id`：跨 Kafka 和 Inbox 的幂等键。
- `Outbox.status / retry_count / next_retry_at / locked_by`：生产端投递状态和并发抢占控制。
- `FileEventPayload.oss_key / sha1 / file_id`：store service 找对象和更新文件状态的依据。
- `Inbox.event_id / status / locked_by / locked_until`：消费端幂等与并发处理锁。
- `DLQFailure.payload / error_message / retry_count / status`：失败恢复所需证据。

## 常见误判与排障顺序

- 误判：写 DB 后直接发 Kafka 就够了。正确理解：进程可能在两步之间崩溃，所以需要 Outbox。
- 误判：Kafka 发送成功就一定不会重复。正确理解：`markSent` 失败会导致 Outbox 重发，重复由 Inbox 吸收。
- 误判：DLQ 是普通错误日志。正确理解：DLQ 是可重放/可恢复的失败事件记录。
- 排障顺序：File/UserFile 是否落库 -> Outbox 是否 new/failed/sent -> Kafka 是否收到 -> Inbox 是否 processing/done -> File.status 是否 finalize -> DLQ 是否有 terminal failure。
