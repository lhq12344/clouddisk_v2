# 00. CloudDisk V2 源码复核学习 Manifest

## 本章定位

本目录用于重新学习 `clouddisk_v2`，顺序按"由深到浅、从入口到服务、从链路到数据结构"组织。目标不是背功能列表，而是能画出链路、解释每层中间件作用、定位关键代码、说明核心字段生命周期。

## 总链路

这套 manifest 的阅读路线按系统运行链路组织：

```text
全局架构 -> OpenResty 入口 -> Drogon Gateway -> JWT/gRPC/配置 -> 账号/文件领域 -> 上传/下载/分片 -> Outbox/Kafka/store scan -> MinIO/前端/AI/MCP -> 构建调试/坑点复盘
```

最终目标不是读完文件，而是能用这些章节定位问题：请求卡在哪一层、状态停在哪一步、哪个数据结构字段能证明当前事实。

## 统一格式约定（全部章节与 03 章同规格）

每一章都以 03 章（`03-cpp-gateway-drogon.md`）为格式标杆，每个小节统一为三段式：

1. **主题段落**：先用自然语言说明这一节讲什么、为什么重要。
2. **代码证据块**：每个小节至少一个，带 `文件名:行号` 锚点。所有代码块均从真实源码摘录，写文档时已逐一 Read 验证；行号会随代码变动漂移，锚点找不到时按"路径 + 符号名"搜索（如 `file.go` 的 `buildObjectKey`）。
3. **解释**：逐条分析代码块，说明它证明了什么、边界在哪里。

章节末尾统一有「阅读检查」自测。每章的证据不是总结性摘录，而是"结论必须能回到一个 `type`、`func`、`ADD_METHOD_TO`、`stub->async()`、`gorm.Transaction`、`Kafka consumer` 或 nginx 指令"。

## 学习验收标准

- 能画出 `Client -> OpenResty -> Drogon Gateway -> Go gRPC service -> MySQL/Redis/MinIO/Kafka` 的主链路。
- 能解释每个中间件在什么层发挥作用：Nacos 配置、Consul 发现、Redis 会话/分片状态、Kafka 异步事件、MySQL 元数据、MinIO 对象、ClamAV 扫描。
- 能说明 `File.status` 从 `pending_scan` 到 `success/infected/scan_failed` 的状态变化。
- 能指出当前真实实现边界：OpenResty upstream 固定到 `127.0.0.1:38080`；gRPC `UploadPart(stream)` 在 file_srv 中返回 `codes.Unimplemented`（消息 "deprecated, use PresignParts + direct multipart upload"），实际走预签名直传/代理。

## 状态转换总览

```text
身份：未登录 -> 登录成功 -> JWT/localStorage -> Gateway attributes -> logout/过期/黑名单
文件：上传完成 -> pending_scan -> success/infected/scan_failed
分片：init -> partial -> completed -> pending_scan -> scan result
异步：Outbox new -> Kafka sent -> Inbox processing -> done/DLQ
前端：pending_scan 轮询 -> success 开放下载/预览；infected/scan_failed 展示阻断
```

每章的细节都应能回到这些状态转换中的某一段。

## 关键数据结构 / 字段总览

- `JWT / Authorization / oss_token`：用户会话身份。
- `X-Request-Id`：全链路日志与排障关联。
- `File / UserFile / File.status / object_key`：文件领域核心。
- `upload_id / oss_upload_id / uploaded_parts`：分片上传恢复核心。
- `Outbox / Inbox / DLQFailure`：异步一致性核心。
- `MCPAPIKey`：MCP 工具调用鉴权核心。

## 常见误判总览

- 入口层和应用网关不是一层：OpenResty 是入口代理，Drogon 是应用网关。
- 上传成功不等于文件可读：必须等扫描变成 `success`。
- Consul 不是 RPC 合同：proto/generated stub 才是合同。
- MinIO 不保存业务权限：权限和状态在业务服务/MySQL。
- 前端不是纯展示：它维护 token、上传任务、断点 session、pending_scan 轮询。

## 证据约定

每章都引用当前仓库路径和函数/结构体名。行号会随代码变动漂移，因此本 manifest 优先使用"路径 + 函数/结构体/配置项"作为稳定锚点，关键处补充当前复核到的行号。

所有代码证据块的来源分四类：

```text
入口证据：forward_part/config/nginx/nginx.conf -> forward_part/gateway/controllers/*.h
转发证据：forward_part/gateway/controllers/*.cc -> proto/* -> backword_part/*/protobuf/*.go
数据证据：backword_part/model/*.go -> internal/*.go
异步证据：file_srv/protobuf/file.go -> file_srv/kafkaproduct.go -> other_srv/store_srv/kafka/*.go
```

验证方法：打开章节中标注的路径，先找结构体/函数名，再看调用点。不要只读文字总结；每个关键判断都应能回到一个 `type`、`func`、`ADD_METHOD_TO`、`stub->async()`、`gorm.Transaction` 或 `Kafka consumer` 代码块。

## 读源码时的已知陷阱（详见 18 章）

- `forward_part/gateway/` 下同时有 `consul.h`（`forward_part/internal/consul.h`）和 `concul.go`（`internal/concul.go`），文件名相似但前者是 C++ 网关的 Consul HTTP 客户端，后者是 Go 服务的注册助手，不要混读。
- 同一服务名在 Account/File/AI 三个 controller 里各有独立 `KArcCache` 缓存，stub 不共享。
- `store_srv` 的消费文件名是 `kafkacunsumer.go`（少一个字母 s），检索时不要拼成 `kafkaconsumer.go`。
