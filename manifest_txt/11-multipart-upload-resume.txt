# 11. 分片上传与断点续传：大文件为什么这样设计

## 本章定位

大文件不走小文件的单个 gRPC stream，而走 multipart 控制面：file service 创建 session、签 part URL、查询已上传 parts、complete 对象；浏览器或 gateway 代理负责把每片 PUT 到 MinIO。断点续传的可信状态来自 Redis session + MinIO list parts，不来自前端本地进度条。

总链路：`UploadManager -> initMultipart -> status/list parts -> presignParts -> PUT parts -> status -> completeMultipart -> upsert File/UserFile -> Outbox scan`。

multipart 的五个控制面接口全部是普通 POST RPC，路由挂在 `jwt_decode` filter 之后：

代码证据：`forward_part/gateway/controllers/FileController.h:35-40`

```cpp
	ADD_METHOD_TO(FileController::Initupload, "/file/initupload", Post, "jwt_decode");
	ADD_METHOD_TO(FileController::PresignParts, "/file/PresignParts", Post, "jwt_decode");
	ADD_METHOD_TO(FileController::Uploadpart, "/file/uploadpart", Post, "jwt_decode");
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
	ADD_METHOD_TO(FileController::Status, "/file/Status", Post, "jwt_decode");
```

解释：

- `Initupload / PresignParts / CompleteMultipart / AbortMultipart / Status` 五条是"控制面"：只传元数据（upload_id、part_numbers），不携带分片字节。
- `/file/uploadpart` 是唯一沾"数据面"的路径，但它是预签名 URL 的 HTTP 代理，不是 gRPC stream（见后文"UploadPart(stream) 已废弃"）。
- nginx 为这些路径配了精确匹配转发，其中 `/file/uploadpart` 关闭了请求缓冲（nginx.conf:176-183 的 `proxy_request_buffering off; proxy_buffering off;`），因为要透传大块 body。

## 源码精读：InitMultipart 同时创建业务 upload_id 和 MinIO upload_id

`backword_part/file_server/file_srv/protobuf/file.go` 的 `InitMultipart` 构造 object key，调用 MinIO 初始化 multipart，并把会话 meta 写进 Redis：


解释（InitMultipart 是整个 multipart 会话的"总开关"）：

- `minio.OptimalPartInfo(fileSize, 0)` 按文件大小计算最优 part 大小和片数；兜底 `totalParts=1, partSize=fileSize`。
- `genUploadID()` 生成的是**业务侧 upload_id**（32 位 hex）；`MinIOMultipartInit` 返回的是 **MinIO 侧 oss_upload_id**。两个 id 通过 Redis meta 的 `oss_upload_id` 字段绑定，前端全程只认业务 upload_id，不接触 MinIO id。
- Redis meta 用 `TxPipelined` 一次写 10 个字段 + `Expire(24h)`（`defaultTTL`，file.go:34）。这些字段分别承担不同职责：`user_id` 做 owner 校验，`object_key/oss_upload_id` 对接 MinIO，`part_size/total_parts` 用于前端切片和 complete 前校验，`status` 记录会话是否已 completed。
- 如果 Redis 写入失败，回滚调用 `MinIOMultipartAbort` 清理 MinIO 侧 upload，避免孤儿 session。
- 注意 InitMultipart 开头（file.go:977-991）会先按 file_hash 查 `files` 表：文件已存在时直接复用对象并返回（`reuseMessage`，file.go:113-130），不创建新 multipart——这是哈希去重在 multipart 入口的体现。

## 源码精读：PresignParts 是控制面，不传输数据面

`PresignParts` 读取 Redis meta 后，为每个 part number 生成 MinIO PUT URL：

代码证据：`backword_part/file_server/file_srv/protobuf/file.go:1046-1087`（PresignParts）

解释：

- 先 `HMGet` Redis meta：session 不存在/过期直接 `NotFound`；owner 校验通过 `ensureMultipartOwner`（file.go:155-164）比较 gRPC 元数据里的 `x-user-id` 与会话 `user_id`，不匹配返回 `PermissionDenied`。

- 每个 part 独立签 PUT URL，过期 `multipartPresignExpiry = 15 * time.Minute`（file.go:35），`expires_at` 一并返回给前端。
- **整个函数不接收、不转发任何 part 字节**——它只确认"这个 upload_id 合法、你被允许上传这些 part"，数据面由浏览器直接打 MinIO。

## 源码精读：CompleteMultipart 是最终业务提交点

`CompleteMultipart` 会 list parts、校验数量、调用 MinIO complete，再落 `File/UserFile` 并写扫描 outbox。先看入口与幂等分支：

代码证据：`backword_part/file_server/file_srv/protobuf/file.go:1093-1129`（CompleteMultipart 入口）

```go

	if req == nil || strings.TrimSpace(req.UploadId) == "" {
		return nil, status.Error(codes.InvalidArgument, "missing upload_id")
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
	}
```

解释：

- 相比 `PresignParts/Status`，这里 `HMGet` 取**全部** meta 字段——complete 需要把文件名/大小/hash 落进 `File` 表，所以业务元数据必须全量带回。
- `status == "completed"` 是幂等分支：前端重试 complete（网络超时后）不会重复触发 MinIO complete 和 outbox，直接返回当前文件状态。

然后校验分片完整性并完成对象：

代码证据：`backword_part/file_server/file_srv/protobuf/file.go:1131-1177`（CompleteMultipart 主体）

```go
	parts, err := listUploadedParts(ctx, objectKey, ossUploadID)
	if err != nil {
		return nil, status.Errorf(codes.Internal, "list multipart parts: %v", err)
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `len(parts) != totalParts` 直接失败（`FailedPrecondition`）：**part 数对不上，MinIO 根本不会执行 complete**，这是"必须传完全部片"的硬保证。
- `MinIOMultipartComplete` 需要每个 part 的 `PartNumber + ETag`——ETag 正是前面 PUT part 时对象存储返回的（前端直传时从响应头拿到，网关代理时从 `resp->getHeader("ETag")` 拿到）。S3 协议要求 parts 按升序提交，`listUploadedParts` 已经排好序。
- `upsertFileAndRelation`（file.go:255-419）在一个事务里完成：按 sha1 查/建 `File`（新记录默认 `pending_scan`）、恢复软删记录、补 `UserFile` 关系；需要扫描时写 `Outbox`（`enqueueScanRequested`，file.go:225-253，topic `file.upload.cmd`）。`requeueScan=false` 是有意的：只有新文件或复用 scan_failed 对象时才投递扫描事件。
- complete 成功后 Redis 会话标记 `completed`（幂等分支依据），返回 `Status: file.Status`——**通常是 `pending_scan`**，直到 store service 消费 outbox 完成 ClamAV 扫描才变成 `success`。前端 UploadManager 也会对 `pending_scan` 任务每 3 秒轮询 `queryFiles` 更新状态（UploadManager.tsx:282-306）。
- 落库失败时删除已 complete 的 MinIO 对象（`MinIODeleteObject`），避免"对象存在但无元数据"的孤儿对象。


解释：再次按升序排序兜底，然后 `CompleteMultipartUpload` 让对象存储把所有 part 拼接成最终对象。complete 是原子的：成功后 `files/<hash>` 就是一个完整可下载对象。

与 complete 配套的取消路径 `AbortMultipart`：读 Redis meta 后中止 MinIO upload 并删除会话，对"会话不存在"幂等处理：

代码证据：`backword_part/file_server/file_srv/protobuf/file.go:1180-1209`（AbortMultipart）

```go
func (s FileServer) AbortMultipart(ctx context.Context, req *AbortReq) (*AbortResp, error) {
	if req == nil || strings.TrimSpace(req.UploadId) == "" {
		return nil, status.Error(codes.InvalidArgument, "missing upload_id")
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- 会话已不存在时（可能已被 TTL 清理）直接返回成功——abort 是尽力而为的清理操作，幂等。
- 已 `completed` 的会话**不再** abort MinIO upload（对象已生成，abort 会把完整对象删掉），只删 Redis key。
- 前端 `abortMultipart`（api.ts:263-268）走 `/file/AbortMultipart`，用于用户取消上传时回收 MinIO 上已上传的孤儿 part（这些 part 在 complete 前不产生可见对象，但会占用存储配额）。

## 状态转换

分片上传有三层状态：前端任务状态、Redis 会话状态、文件安全状态。

```text
用户选择大文件 -> hashing -> initialized -> uploading -> partial/resumable -> completed -> pending_scan
pending_scan -> 扫描 clean -> success
pending_scan -> 扫描 infected -> infected
pending_scan -> 扫描失败耗尽重试 -> scan_failed/DLQ
initialized/uploading -> 用户取消或异常清理 -> abort -> Redis meta 删除 + MinIO multipart abort
```

可信状态来源不同：

```text
localStorage/sessionStorage -> 只保存前端恢复入口 upload_id
Redis meta -> 保存 owner、object_key、part_size、total_parts、oss_upload_id
MinIO list parts -> 已上传 part 的事实来源
MySQL File.status -> complete 后的安全状态来源
```

## 关键数据结构 / 字段

- `upload_id`：file service 生成的业务会话 id，前端可见。
- `oss_upload_id`：MinIO multipart upload id，存 Redis，不直接暴露为业务状态。
- `part_size / total_parts`：前端切片和 complete 校验依据。
- `uploaded_parts`：从 MinIO list parts 得到，是断点续传事实来源。
- `object_key`：最终合并成一个 MinIO 对象的位置。
- `File.status`：complete 后仍通常是 `pending_scan`，不是可读终态。

## 常见误判与排障顺序

- 误判：浏览器本地进度就是断点续传真相。正确理解：本地 session 只找回 upload_id，MinIO list parts 才是真相。
- 误判：proto 里有 `UploadPart(stream)` 就是主链路。正确理解：Go 实现已返回 Unimplemented，主链路是 presigned PUT。
- 误判：complete 后文件马上可下载。正确理解：complete 只表示对象合并完成，还要进入 `pending_scan`。
- 排障顺序：InitMultipart Redis meta -> PresignParts owner 校验 -> PUT part/ETag -> Status list parts -> Complete parts 数量校验 -> DB/Outbox -> store scan。

## 阅读检查

- 能画出 `UploadManager -> initMultipart -> Status/list parts -> presignParts -> PUT parts（直传或 gateway 代理）-> Status -> completeMultipart -> upsert File/UserFile -> Outbox scan` 完整链路。
- 能解释 Redis meta（业务会话）、MinIO upload id（对象存储会话）、本地 session（前端恢复入口）三者的区别与绑定关系。
- 能说明为什么 `Status`（MinIO list parts）是断点续传的可信依据，前端进度条为什么只是估读。
- 能明确 `UploadPart(stream)` 不是当前主链路（`file.go:1089-1091` 返回 `codes.Unimplemented`），以及 `/file/uploadpart` 是预签名 URL 的 HTTP 代理（含 host 白名单与路径/参数校验）。
- 能从 `InitMultipart` 追到 `CompleteMultipart` 和 Outbox：part 数校验、ETag 收集、`upsertFileAndRelation` 事务、`requeueScan=false` 的语义。
- 能说出 `AbortMultipart` 与 `CompleteMultipart` 的分工：前者回收未完成会话，后者幂等提交。
