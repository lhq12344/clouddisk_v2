# 09. 小文件上传：从 HTTP body 到 MinIO 和扫描队列

## 本章定位

小文件上传要按"数据面"和"控制面"一起读：文件字节从浏览器一路流到 MinIO，控制信息从 header/JWT 变成 gRPC meta，再变成 MySQL 元数据和 Outbox 扫描事件。最终用户能不能下载，不由上传接口决定，而由 store service 扫描后的 `File.status` 决定。

总链路：`UploadManager -> ApiService.simpleUpload -> OpenResty /file/upload -> Drogon FileController.LoadFile -> file_srv.UploadFile(stream) -> MinIOUploadStream -> upsertFileAndRelation -> Outbox -> store_srv scan`。

- JWT 从 `localStorage('oss_token')` 取出注入 `Authorization`；`X-Request-Id` 由前端生成，OpenResty/Drogon/Go 全链路透传。

## 前端任务调度：5MB 以下走小文件，以上走分片

`forward_part/static/components/UploadManager.tsx:15` 定义了分界：`SIMPLE_UPLOAD_THRESHOLD = 5 * 1024 * 1024`。`processUpload`（`UploadManager.tsx:220`）先算 SHA-256，再按大小分流。

代码证据：`forward_part/static/components/UploadManager.tsx:26-30`

```ts
const calculateHash = async (data: ArrayBuffer): Promise<string> => {
  const hashBuffer = await crypto.subtle.digest('SHA-256', data);
  const hashArray = Array.from(new Uint8Array(hashBuffer));
  return hashArray.map((b) => b.toString(16).padStart(2, '0')).join('');
};
```

代码证据：`forward_part/static/components/UploadManager.tsx:220-239`

```ts

      updateTask(taskId, { status: 'uploading', detail: 'hashing' });
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
  };
```

解释：

- 阈值 5MB：小于走 `simpleUpload`（本章），大于等于走 `uploadMultipart`（第 11 章详读）。
- 小文件也会先整个读进内存算 SHA-256——hash 是内容身份，上传链路和秒传都依赖它。
- 服务器返回非 2xx 时，错误里可能带着 `uploadResponse`（含 `status/message`，如 `infected`），前端据此展示状态而不是一律报"上传失败"。
- 计算 hash 期间任务状态是 `hashing`，说明上传前有一个可感知的等待阶段。

解释：

- `io.Pipe` 是同步管道：主 goroutine 写入多少，MinIO 后台 goroutine 就读走多少，内存里只滞留未消费的块，不整文件缓冲。

## 状态转换

小文件上传要按两个维度理解状态：前端上传任务状态和后端文件安全状态。

```text
前端选择文件 -> hashing -> uploading -> pending_scan/success/infected/scan_failed/error
```

后端文件状态更关键：

```text
HTTP body 接收中 -> Drogon gRPC stream 转发中 -> MinIO object stored -> MySQL File/UserFile 已落库 -> pending_scan
pending_scan -> store service 扫描 clean -> success -> 下载/预览接口允许签 URL
pending_scan -> ClamAV FOUND -> infected -> 删除 object，前端禁用下载
pending_scan -> 扫描失败耗尽重试 -> scan_failed/DLQ -> 需要排障或重试恢复
```

这组状态说明：`UploadFileResp{Status: pending_scan}` 不是失败，而是异步扫描还没收敛；只有 `success` 才是可读终态。

## 关键数据结构 / 字段

- `UploadFileMeta.user_id`：由 Gateway 从 JWT 身份写入，是文件归属校验的依据。
- `UploadFileMeta.file_hash`：前端计算出的内容身份，用于 object key、去重、UserFile 关联。
- `UploadFileMeta.file_size`：声明大小，Go 服务用实际写入字节数校验 size mismatch。
- `File.sha1 / File.object_key`：内容对象身份和 MinIO 存储位置。
- `File.status`：安全状态门禁，上传后通常先是 `pending_scan`。
- `Outbox.event_id / payload`：扫描事件，保证上传落库后 store service 能继续处理。

## 常见误判与排障顺序

- 误判：上传接口返回 200 就能下载。正确理解：200 只表示对象/元数据已进入系统，是否可读看扫描后的 `File.status`。
- 误判：OpenResty 负责上传业务。正确理解：OpenResty 只做入口代理；协议转换在 Drogon，存储在 file service/MinIO。
- 误判：小文件一次性读入后保存。正确理解：Gateway 到 Go 是 gRPC stream，Go 到 MinIO 是 `io.Pipe` 流式上传。
- 排障顺序：前端 hash/headers -> OpenResty body 代理 -> Drogon `LoadFile/UploadFileProxy` -> gRPC stream -> `UploadFile` size 校验 -> MinIO -> DB/Outbox -> store scan。
