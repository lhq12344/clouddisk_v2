# 01. 架构全景：从用户请求到对象存储

## 本章定位

本章提供“上帝视角”：先把 Client、OpenResty、Drogon Gateway、Go gRPC 服务、MySQL、Redis、Kafka、MinIO、ClamAV、Consul、Nacos 放到同一张图里，再区分同步请求链路和异步扫描链路。读完本章后，再进入 02–18 的各层细节。

## 总链路

```text
同步业务链路：Client -> OpenResty -> Drogon Gateway -> gRPC service -> MySQL/Redis/MinIO -> HTTP response
异步扫描链路：file_srv -> Outbox -> Kafka -> store_srv -> MinIO stream -> ClamAV -> File.status
配置发现链路：Nacos -> ViperConf -> global clients；Go service -> Consul register；Gateway -> Consul discover/cache
前端状态链路：React state -> ApiService -> Gateway response -> pending_scan 轮询 -> success/infected/scan_failed
```

本章只讲模块协作和职责边界，不深入每个函数实现；函数级源码证据放在后续章节展开。

## 中间件作用位置

- Nacos：Go 服务初始化配置源，见 `internal/viper_config_centre.go` 和 `scripts/nacos-config/clouddisk.json`。
- Consul：服务发现/注册；Go 服务启动时注册，Drogon 网关查询实例，见 `internal/concul.go`、`forward_part/internal/consul.cpp`、`forward_part/gateway/ConsulRegister.cpp`。
- Redis：JWT 白名单/黑名单、注册验证码 pending 数据、multipart session meta；入口在 `gateway` Redis client 与 Go `internal.RedisClient`。
- MySQL：账号、文件元数据、用户文件关系、Outbox/Inbox/DLQ 状态，模型在 `backword_part/model/`。
- Kafka：异步事件总线；file service 写 outbox 后 dispatcher 发送，store service 消费。
- MinIO：当前主对象存储，支持 PutObject、预签名下载、multipart。
- AliOSS：有客户端封装，但主上传/扫描链路以 MinIO 为主。
- ClamAV：store service 对对象流做病毒扫描，决定文件最终可用状态。

## 同步链路和异步链路

同步链路解决“请求是否被接收、元数据是否创建、URL 是否返回”。例如登录、文件列表、小文件上传接收、分片初始化都走 HTTP -> Drogon -> gRPC。

异步链路解决“上传后的文件是否安全可用”。`file_srv` 在 DB 事务内创建 `File` 和 `Outbox`，`OutboxDispatcher` 发送 Kafka，`store_srv` 扫描对象并把 `File.status` 改为 `success/infected/scan_failed`。

解释：

- 同步链的终点是“对象已进 MinIO + 元数据已落库”：`UploadFile` 把 gRPC stream 收到的数据块通过 `io.Pipe` 喂给 `MinIOUploadStream`，全程流式，不落本地临时文件。
- 同步链上返回给前端的 `Status` 通常不是 `success` 而是 `pending_scan`——`upsertFileAndRelation` 创建 `File` 时初始状态就是 `model.FilePendingScan`，并在**同一个 DB 事务内**写入一条 `Outbox` 记录（`enqueueScanRequested`），这是 outbox 模式的落点：业务提交和事件入队要么都成功、要么都失败。
- 异步链从 `Outbox` 起步：`file_srv` 的 `OutboxDispatcher`（kafkaproduct.go）轮询 claim 未发送记录，`sendOne` 发到 Kafka topic `file.upload.cmd`，并把 `Outbox` 标为 `SENT`；失败则标 `FAILED` 带指数退避重试。
- 异步链的终点在 store_srv：`processMessageInternal` 消费消息后先做 Inbox 幂等（`tryBeginInbox`），再 `scanObject`（MinIO 取对象流 -> ClamAV），最后 `finalizeClean`（status=success）或 `finalizeInfected`（status=infected 且删除对象）或标记 `scan_failed` 并进 DLQ。
- 读源码时只要记住：`UploadFile` 返回“上传已接收”不代表“文件可下载”，`File.status == success` 才是可下载的充分条件。

## 当前实现和理想图的差异

OpenResty 目录有 Lua 服务发现文件 `lua/consul_service.lua` 与 `lua/balancer.lua`，但当前 `nginx.conf` 中 `upstream cloudisk_backend` 固定为 `server 127.0.0.1:38080`。所以学习时不要把它误读成已经启用 Lua 动态上游；真实动态发现主要发生在 Drogon 到 gRPC 服务之间。

## 源码精读：全链路如何从源码拼出来

### 1. 外部流量先进入 OpenResty，再固定转给 Drogon

代码证据：`forward_part/config/nginx/nginx.conf`

```nginx
upstream cloudisk_backend {
    server 127.0.0.1:38080;
}
# ... 省略非关键行，保留完整路径/配置锚点见上文 ...
}
```

解释：

- 当前 OpenResty 的 `cloudisk_backend` 是固定地址 `127.0.0.1:38080`，也就是 C++ Drogon Gateway 的监听端口（gateway/main.cc 的 `addListener(listenHost, port)`，端口来自 `config.json`）。
- `/file/upload` 这类 API 在 OpenResty 层没有任何业务逻辑，只是 `proxy_pass` 到 gateway；入口层做的是转发、CORS、Request ID、buffering 控制（详见 02 章）。
- 所以全景图第一段应画成 `Client -> OpenResty -> Drogon`，不能画成 `Client -> OpenResty -> Go service`。

### 2. Go 服务以 gRPC server 方式暴露内部能力

代码证据：`backword_part/file_server/file_srv/main.go`

```go
	// ---- 2. 创建 gRPC Server ----
	grpcServer := grpc.NewServer(
		grpc.UnaryInterceptor(internal.RequestIDUnaryInterceptor()),
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
	}
```

解释：

- 启动顺序：`ListenAutoPort()` 找随机空闲端口 -> `grpc.NewServer`（挂 RequestID 拦截器）-> 注册 FileServiceServer -> 注册 health -> Consul 注册 -> 启动 outbox dispatcher -> `Serve`。gRPC server 与异步投递器在同进程共存。
- `RequestIDUnaryInterceptor`/`RequestIDStreamInterceptor`（internal/interceptor.go）从 gRPC metadata 提取 `x-request-id` 注入 context——这是 OpenResty 生成的 Request ID 进入 Go 服务的方式。
- 同一个 main.go 把 file service 分成两个角色：`RegisterFileServiceServer` 是同步 gRPC API 供 Drogon 调用；`NewOutboxDispatcher(...).Start(ctx)` 是异步事件投递器，把 DB outbox 中的扫描事件发到 Kafka。
- 这解释了为什么文件上传链路里同时存在同步返回和异步扫描：上传接口负责接收和落元数据，扫描状态由后续事件链路推进。

解释：

- 三个业务服务（account_srv/file_srv/AI_srv）共用同一套“随机端口 + gRPC server + Consul 注册 + health”模板，只有注册的 server 实现与 Consul 服务名不同（`account_srv`/`file_srv`/`AI_srv`）。
- 每个服务的 proto 文件是这份模板的“合同来源”：`proto/account_srv/account.proto` 定义 `accountService`（Signin/Signup/VerifyCode/Userinfo），`proto/file_srv/file.proto` 定义 `fileService`（查询/上传/下载/分片等 13 个 RPC），`proto/AI_srv/ai.proto` 定义 `AIService`（AIrequest）。Drogon 网关和 Go 服务都从这些 proto 生成各自的客户端/服务端代码。
- 注册到 Consul 的是随机端口：`ListenAutoPort` 用 `net.Listen("tcp", ":0")` 拿到空闲端口后直接 `Serve(lis)`，绝不再 `Listen` 一次——这也是 main.go 注释反复强调“只监听一次”的原因。因此 Consul 里登记的地址是每次启动都会变的，必须靠服务发现而不能写死。

### 4. Gateway 不是透明代理，而是 HTTP/gRPC 编排层

代码证据：`forward_part/gateway/controllers/FileController.h`

```cpp
	ADD_METHOD_TO(FileController::filequeryinfo, "/file/query", Post, "jwt_decode");
	ADD_METHOD_TO(FileController::LoadFile, "/file/upload", Post, "jwt_decode");
	ADD_METHOD_TO(FileController::CompleteMultipart, "/file/CompleteMultipart", Post, "jwt_decode");
```

解释：

- 浏览器看到的是 HTTP API，但这些 API 先进入 Drogon controller。`jwt_decode` 也证明鉴权发生在 gateway 层，而不是 OpenResty 层（filters/jwt_decode.cc 校验 `Authorization: Bearer`、Redis 黑名单/白名单后把 `ID/Name` 注入 request attributes）。
- gateway 拿到 JWT 注入的身份后，通过 proto 生成的 `fileService::Stub` 调用 Go 侧 gRPC（`FindService("file_srv")` 走 Consul + 缓存），再把 gRPC response 转回 JSON。这套编排细节见 03 章。
- 也就是说，OpenResty 到 Drogon 是“转发”，Drogon 到 Go 是“协议转换 + 编排”，两层边界不要混淆。

### 5. 文件最终可用性由 Store service 决定

代码证据：`other_srv/store_srv/kafka/kafkacunsumer.go`

```go
	signature, infected, err := c.scanObject(ctx, payload.OssKey, payload.Size)
	if err != nil {
		...
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
	return c.finalizeClean(ctx, &payload)
```

解释：

- 这段代码是全景图里异步链路的核心证据：上传后文件通常先是 `pending_scan`，真正变成 `success` 或 `infected` 的地方不是上传接口，而是 store service 消费 Kafka 后的扫描分支。
- `scanObject`（kafkacunsumer.go 的 `scanObject`）从 MinIO 拉对象流（`MinIOGetObjectStream`）喂给 ClamAV（`ScanReaderWithClamAV`），`finalizeClean` 在事务里把 `File.status` 改为 `success`，`finalizeInfected` 先把对象删掉再落 `infected`。
- 完整事件链（可对照 12 章、13 章细读）：`upsertFileAndRelation` 事务写 File(pending_scan)+Outbox -> dispatcher 发 Kafka `file.upload.cmd` -> store_srv `tryBeginInbox` 幂等 -> 扫描 -> `finalizeClean/Infected` -> `markInboxDone`；失败进入 `.dlq` topic 由低频 DLQ consumer 重放。

### 6. 该章结论

源码共同证明当前架构应按两条链读：

```text
同步请求链：Client -> OpenResty -> Drogon Gateway -> Go gRPC service -> MySQL/Redis/MinIO
异步扫描链：file_srv Outbox -> Kafka -> store_srv Inbox -> MinIO stream -> ClamAV -> MySQL status
```

读源码时只要先分清这两条链，就不会把“上传成功”误认为“文件已可下载”，也不会把 OpenResty 的入口代理职责误解成业务网关职责。

## 状态转换

全局架构中最重要的跨层状态有三条：

```text
用户身份：未登录 -> Signin -> JWT -> Gateway request attributes -> gRPC metadata/业务参数
文件安全：uploaded/object stored -> pending_scan -> success/infected/scan_failed
异步事件：Outbox new -> Kafka sent -> Inbox processing -> done/DLQ
```

这些状态分别跨越前端、Gateway、Go 服务、数据库、Kafka 和 store service。学习时要避免只看单个服务的局部成功。

## 关键数据结构 / 字段

- `JWT / Authorization`：用户身份跨 HTTP 层传递的凭证。
- `X-Request-Id`：跨入口、网关、gRPC、Kafka、store service 的排障关联字段。
- `File / UserFile`：内容对象与用户文件关系的分离。
- `File.status`：上传、扫描、下载/预览之间的核心状态门禁。
- `Outbox / Inbox / DLQFailure`：异步一致性三件套。
- `Consul service name`：Gateway 找到 gRPC 后端的服务发现 key。

## 常见误判与排障顺序

- 误判：OpenResty、Drogon、Go Gateway 是一层。正确理解：OpenResty 是入口代理，Drogon 是应用网关，Go 服务是内部业务服务。
- 误判：上传成功等于文件可用。正确理解：上传只进入 `pending_scan`，store service 扫描后才进入可读状态。
- 误判：Consul 定义 RPC。正确理解：Consul 只发现地址，RPC 合同来自 proto/generated stub。
- 排障顺序：入口请求 -> Gateway 路由/filter -> gRPC 调用 -> 服务内部 DB/Redis/MinIO -> Outbox/Kafka/store scan -> 前端状态轮询。
