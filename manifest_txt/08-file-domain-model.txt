# 08. 文件领域模型：File、UserFile、Outbox、Inbox、DLQ

## 本章定位

本章先讲文件领域模型。文件功能看起来是上传/下载，但真正的领域核心是“内容对象”和“用户文件关系”分离，以及“业务落库”和“异步扫描事件”一致性。读懂模型后，再读上传、下载、分片会简单很多。

## 总链路

```text
上传/complete -> File(content object) + UserFile(user relation) -> Outbox(FileScanRequested)
Outbox -> Kafka -> store_srv -> Inbox(event idempotency) -> File.status update
失败收敛 -> DLQFailure -> 人工/自动恢复
下载/预览 -> UserFile owner 校验 -> File.status/object_key -> presigned URL
```

模型是后续所有章节的“名词表”：不分清 `File` 和 `UserFile`，就无法理解秒传、重命名、扫描状态和下载门禁。

## 核心模型概览

这一章要建立的五个概念：

| 模型 | 一句话职责 |
| --- | --- |
| `File` | 内容对象元数据：hash、大小、扫描状态、object key |
| `UserFile` | 用户与内容的拥有关系：谁以什么文件名持有哪个内容 |
| `Outbox` | 生产端本地事件表：保证"落库"与"事件投递"原子性的起点 |
| `Inbox` | 消费端幂等表：保证同一事件只被处理一次 |
| `DLQFailure` | 消费失败恢复记录：无法处理的消息落在这里，供人工/自动补偿 |

## File：内容对象元数据

`backword_part/model/filedb.go:16` 定义 `File`。它代表内容对象，不等于用户看到的文件名——表里没有任何"文件名"字段，只有 hash、大小、扫描状态、对象存储 key 和内容类型。

代码证据：`backword_part/model/filedb.go:16-25`

```go
type File struct {
	gorm.Model
	Sha1        string     `gorm:"type:varchar(64);not null;uniqueIndex"` // 历史字段名，当前实际保存 SHA-256 内容哈希
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

`Status` 的取值不是随意字符串，是同文件定义好的四个常量（`filedb.go:9-14`）：

代码证据：`backword_part/model/filedb.go:9-14`

```go
const (
	FilePendingScan = "pending_scan"
	FileSuccess     = "success"
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
)
```

解释：

- 没有文件名字段：同一个 `File` 可以被多个用户、多个文件名引用，文件名放在 `UserFile` 里。
- `Sha1` 是历史字段名，代码注释明确"当前实际保存 SHA-256 内容哈希"，学习时不要机械理解成 SHA-1，语义是"内容哈希"。
- 字段名是 `Size`（不是 `FileSize`），上传完成和读取校验都拿它和实际字节数对比。
- `ObjectKey` 是 MinIO 对象 key，通常由 `buildObjectKey(hash)` 得到 `files/<hash>`（`backword_part/file_server/file_srv/protobuf/file.go:57-59`）。
- `Status` 和 `ScannedAt` 都有索引：扫描链按状态批量查表、回写扫描时间。
- `ScanDetail` 保存扫描失败/感染原因，下载接口会把它的内容返回给用户。
- 四个状态中只有 `success` 允许下载/预览；`pending_scan` 是"等待扫描完成"，不是失败。

## UserFile：用户文件关系

`filedb.go:27` 定义 `UserFile`。它把用户、文件内容和用户看到的文件名关联起来，这样多个用户或同一用户不同文件名可以复用同一个内容 hash。

代码证据：`backword_part/model/filedb.go:27-36`

```go
// UserFile 用户文件关系表（谁拥有这个文件）
type UserFile struct {
	gorm.Model
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- 业务实体是"谁以什么名字拥有什么内容"：`AccountID + FileID + Name` 三列。
- 唯一索引 `uk_account_file_name` 的含义是：同一账号下同名文件关系唯一，而不是全局文件名唯一。两个不同用户可以各自持有一个叫 `report.pdf` 的文件。
- `File` 和 `Account` 是 GORM association 声明：`FileID` 关联 `files.id`，`AccountID` 关联 `accounts.id`（`Account` 定义在 `backword_part/model/accountdb.go:5-15`）。
- 因为引用的是 `FileID` 而不是 hash，复用/删除内容时只动关系不动内容。

## 关系的维护：ensureUserFile 如何保证"同 hash 复用"

`UserFile` 复用的难点在软删除：用户删过文件后，`user_files` 里可能留着一行 `deleted_at` 非空的关系，直接 `INSERT` 会撞唯一索引。`backword_part/file_server/file_srv/protobuf/file.go:166` 的 `ensureUserFile` 处理了这几种情况。

代码证据：`backword_part/file_server/file_srv/protobuf/file.go:166-206`

```go

	var existing model.UserFile
	err := tx.Unscoped().
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- 第一步用 `Unscoped()` 查——连软删除行一起查，因为软删除行占着唯一索引。
- 找到且未删除，直接返回（关系已存在，无需写入）。
- 找到但已软删除，把 `deleted_at` 清掉恢复关系。
- 没找到时用 `OnConflict{DoNothing: true}` 插入——并发下两个请求同时插入，谁撞了唯一索引都不报错。
- 插入后再次 `Unscoped()` 把可能残留的软删除行恢复。三段式查询保证唯一索引 `uk_account_file_name` 不会被软删除行挡住。

## FileEventPayload：扫描事件的载体

`filedb.go:63` 的 `FileEventPayload` 是发往 Kafka 的业务事件 payload。它把事件身份（`event_id`）、文件身份（`file_id`、`sha1`、`oss_key`）、归属（`user_id`）、大小与类型带给 store service，让消费端不用回头查库就能知道扫哪个对象。

代码证据：`backword_part/model/filedb.go:63-73`

```go
type FileEventPayload struct {
	TxID        string `json:"tx_id"`
	EventID     string `json:"event_id"`
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `EventID` 是幂等键，Inbox 用它去重。
- `OssKey` 告诉 store service 扫描哪个 MinIO 对象；`FileID` 让它回写 `files` 表。
- `TxID` 用于把同一上传流程的多条事件串联起来。
- 下载链还有一份姊妹 payload `DownloadCmdPayload`（`filedb.go:53-62`），结构几乎相同，供下载事件使用。
- `EventType` 当前主要是 `FILE_SCAN_REQUESTED`（`filedb.go:49`），预留了版本演进与路由空间。

## Outbox：生产端本地事件表

`filedb.go:74` 的 `Outbox` 是本地事务事件表。作用是让"文件元数据落库"和"扫描事件待发送"在同一个 DB transaction 中完成：事务提交后事件必然在表里；dispatcher 从表里读事件发 Kafka，而不是业务代码直接发 Kafka。

代码证据：`backword_part/model/filedb.go:74-90`

```go

```

## Inbox：消费端幂等表

`filedb.go:100` 的 `Inbox` 是消费端幂等表。store service 收到 Kafka message 后先抢占/检查 inbox，避免同一事件重复扫描、重复落库。它的主键直接是 `event_id`，因为幂等键就是事件 ID。

代码证据：`backword_part/model/filedb.go:92-111`

```go
type InboxStatus string

const (
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `EventID` 是主键：同一事件重复投递（Kafka 至少一次语义）只会命中同一行，天然去重。
- `PROCESSING/DONE/DLQ` 三个状态对应"正在处理/已完成/已进死信"。
- `LockedBy/LockedUntil` 是处理锁：多实例消费时只有一个实例能抢占，超时后其他实例可接续。
- `DLQFailureID` 把幂等表和死信记录表关联起来：失败消息进 DLQ 后，可以在 inbox 里看到去向。
- `Attempts/LastError` 记录重试次数和最近失败原因，是排障入口。

## DLQFailure：消费失败恢复记录

`backword_part/model/dlq.go:18` 定义 DLQ 失败记录。它保存 Kafka topic/partition/offset、事件上下文、失败原因、状态和恢复信息，用于后续人工或自动补偿。

代码证据：`backword_part/model/dlq.go:7-50`

```go
// DLQStatus DLQ 消息状态
type DLQStatus string

// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `Topic/Partition/Offset` 三件套（联合索引 `idx_topic_offset`）定位 Kafka 里的原始消息，失败后可以精确重放。
- `OriginalKey/OriginalValue` 保存原始消息字节，不依赖 Kafka 消息是否还在。
- `ErrorCategory` 区分 `retryable/non_retryable/unknown`：决定自动重试还是等人工处理。
- `Status` 的 `pending -> retrying -> failed/resolved` 是补偿流程的状态机（`dlq.go:10-15`）。
- 表名由 `TableName()` 显式指定为 `dlq_failures`（`dlq.go:52-55`）；`DLQMetrics`（`dlq.go:57-79`）是内存监控结构，不落库。

事务收尾部分（`file.go:404-413`）把三件事串起来：

代码证据：`backword_part/file_server/file_srv/protobuf/file.go:404-413`


解释：

- 第一件事：按 `sha1` 查内容对象，没有就创建（`Status` 直接是 `pending_scan`），并置 `shouldEnqueue`。
- 第二件事：`ensureUserFile` 建立/恢复用户关系，与内容对象同事务。
- 第三件事：`shouldEnqueue` 为真时写 Outbox 扫描事件，也在同一事务里。
- 这样不会出现"用户看到了文件关系，但没有扫描事件"的不一致状态：要么三件事一起提交，要么一起回滚。
- 并发细节：`Create` 撞唯一索引时（`duplicateKey`，`file.go:208-214`）回查已有行而不是报错——同一 hash 并发上传也不会产生两个 `File`。
- 查询侧（第 10 章详读）：`findOwnedUserFile`（`file.go:553-573`）用 `Preload("File")` 把关系和内容一次取回；`Filequeryinfo`（`file.go:871-919`）遍历 `UserFile` 列表拼出用户看到的文件列表。

解释：

## 关键数据结构 / 字段

- `File.sha1`：内容 hash，是对象去重和关联的核心身份。
- `File.object_key`：MinIO 中的对象位置。
- `File.status`：安全状态，控制下载/预览是否放行。
- `File.scan_detail / scanned_at`：扫描结果和时间。
- `UserFile.account_id / file_id / filename`：用户视角文件关系。
- `Outbox.event_id / payload`：生产端异步事件记录。
- `Inbox.event_id / status`：消费端幂等处理记录。
- `DLQFailure.payload / error_message`：失败恢复证据。

## 常见误判与排障顺序

- 误判：一个用户文件就是一个对象。正确理解：多个 `UserFile` 可以指向同一个 `File` 内容对象。
- 误判：`File.sha1` 只是历史字段名。正确理解：它承担当前内容 hash 语义。
- 误判：Outbox/Inbox/DLQ 是扫描服务细节。正确理解：它们是文件状态异步一致性的核心模型。
- 排障顺序：UserFile 归属 -> File 内容对象 -> File.status/object_key -> Outbox event -> Inbox/DLQ -> store service finalize。
