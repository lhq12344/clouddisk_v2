# 13. Store Service 与病毒扫描：文件什么时候真正可用

## 本章定位

`store_srv` 不是上传服务。对象已经由 file service 写入 MinIO，store service 的职责是消费扫描事件、读取对象流、调用 ClamAV、更新 `File.status`，并处理 retry/DLQ。第 09/11 章只把文件推进到 `pending_scan`；本章才决定它是否变成 `success`。

总链路：`Kafka FileScanRequested -> tryBeginInbox -> load File -> MinIOGetObjectStream -> ScanReaderWithClamAV -> finalizeClean/finalizeInfected/markFileScanFailed`。

File 的四个状态常量定义在 model 层，是本章与第 08/10 章之间的契约：只有 `success` 的文件才允许下载/预览。读者应先回顾第 12 章的 outbox/inbox/DLQ 机制，本章是它在上传扫描场景的具体应用。

代码证据：`backword_part/model/filedb.go:9-14`

```go
const (
	FilePendingScan = "pending_scan"
	FileSuccess     = "success"
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
)
```

解释：

- 四个状态构成文件生命周期：pending_scan（已落 MinIO，等待扫描）→ success（扫描通过，可用）/ infected（检出病毒，禁用）/ scan_failed（未能确认安全，禁用）。
- 第 10 章下载/预览的放行条件只认 success，原因见本章"失败路径不能默认放行"一节。
- `scan_failed` 不是终态：用户重传同一 hash 时 file_srv 的 `upsertFileAndRelation`（第 12 章）会把它重置回 pending_scan 并重新投递扫描事件（requeueScan 逻辑）。

## 源码精读：ClamAV 使用 INSTREAM 协议

ClamAV daemon（clamd）通过文本协议与客户端通信。扫描大文件必须用 INSTREAM 模式：客户端先发 `nINSTREAM\n` 命令，然后反复发送"4 字节大端长度 + 数据块"，最后发一个 0 长度块表示流结束，daemon 回复一行结果（`stream: OK` 或 `stream: <签名> FOUND`）。整个过程中文件内容流式转发，不落盘、不进内存。

## 源码精读：infected 会删除对象并记录原因

感染文件的处理不是只改状态，还会先删除 MinIO object。删除成功（或对象本来就不存在）后，在事务里把 File 置为 infected、scan_detail 存病毒签名，并把 Inbox 置 DONE。这解释了为什么 infected 文件必须禁止下载/预览：对象可能已经被删除，业务状态也明确标记为不安全。

## 源码精读：失败路径不能默认放行

扫描连接失败、对象读取失败、DB 更新失败会走 retry/backoff；耗尽重试后由 handleTerminalFailure 标记 `scan_failed` 并进 DLQ。`scan_failed` 的语义是"未能确认安全"，不是"安全"。所以第 10 章只允许 `success` 是合理的：任何未确认路径都是拒绝服务。

## 状态转换

store service 是文件安全状态的最终推进者。

```text
pending_scan -> Kafka FileScanRequested 被消费 -> Inbox processing
Inbox processing -> MinIO stream + ClamAV OK -> File.success + Inbox.done
Inbox processing -> ClamAV FOUND -> 删除 MinIO object -> File.infected + Inbox.done
Inbox processing -> 临时错误 -> retry/backoff -> 再次扫描
Inbox processing -> 不可重试或重试耗尽 -> File.scan_failed + DLQ
```

下游影响：

```text
success -> 第 10 章下载/预览允许签 URL
infected -> object 被删除，前端展示 Blocked，下载/预览返回 409
scan_failed -> 未确认安全，前端展示 Scan Failed，下载/预览返回 409
```

## 关键数据结构 / 字段

- `FileEventPayload.event_id`：连接 Kafka event、Inbox 和 DLQ 的幂等键。
- `FileEventPayload.oss_key`：store service 从 MinIO 读取对象流的 key。
- `File.status`：扫描结果写回的核心业务状态。
- `File.scan_detail`：感染签名或扫描失败原因。
- `Inbox.status / locked_by`：保证同一事件只有一个 consumer 做最终副作用。
- `ClamAVVerdict.infected / signature`：决定 `success` 还是 `infected` 的扫描结果。

## 常见误判与排障顺序

- 误判：store service 是上传服务。正确理解：它消费已上传事件，负责扫描和状态终态。
- 误判：扫描失败可以默认放行。正确理解：scan_failed 表示未确认安全，必须禁止下载。
- 误判：infected 只改 DB 状态。正确理解：还会删除 MinIO object，避免继续传播。
- 排障顺序：Kafka event payload -> Inbox 是否拿锁 -> MinIO object stream -> ClamAV 连接/INSTREAM 回复 -> finalizeClean/finalizeInfected -> scan_failed/DLQ。

## 阅读检查

- 能说明 `pending_scan -> success/infected/scan_failed` 的状态变化在哪里完成。
- 能解释 ClamAV INSTREAM 的基本协议形态（命令、分块、0 长度结束、一行回复）。
- 能说明为什么 infected 要删除 object，以及 NoSuchKey/NotFound 为什么不算删除失败。
- 能定位 `tryBeginInbox`、`scanObject`、`ScanReaderWithClamAV`、`finalizeClean/finalizeInfected`、`markFileScanFailed`。
- 能说清 finalizeClean/finalizeInfected 里"File 更新 + Inbox DONE"为什么必须在同一事务。
- 能解释为什么扫描失败不能默认放行：scan_failed 的语义是"未能确认安全"，不是"安全"。
- 能区分可重试错误（timeout/connection/temporary）与不可重试错误（invalid payload/file not found），并说出各自的收敛路径。
- 能说出 store_srv 从哪个 topic 消费、属于哪个 consumer group、DLQ topic 叫什么，以及 offset 为什么手动提交。
- 能画出 INSTREAM 的字节序列，并指出排查扫描卡顿时要检查的三段（MinIO stream、clamd 连接、回复解析）。
