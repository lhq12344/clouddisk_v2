# 06. 配置中心与共享基础设施：Nacos/Viper 热更新与全局客户端

## 本章定位

所有 Go 服务启动时的第一件事是读配置。配置源是 Nacos，解析器是 Viper，落点是 `internal` 包的全局结构 `ViperConf`。`internal/` 同时承载 DB、Redis、MinIO、Kafka、Consul、JWT、ClamAV 等全局客户端 —— 它们不依赖任何业务服务，但每个业务服务都依赖它们。

关键机制是 Go 的 `init()`：业务服务的 `main.go` 只要 `import "go_test/internal"`，包级变量和 `init()` 就会在 `main()` 执行前自动运行。所以"读配置 + 建全局客户端"这件事不需要任何业务代码显式调用，它是每个 Go 服务进程启动的隐含前置步骤。

## 总链路

```text
服务进程启动 -> import go_test/internal -> init() -> Nacos GetConfig -> Viper.Unmarshal -> ViperConf
ViperConf -> InitRedis/Initdb/InitConsul/InitKafkaProducer/InitAli/InitMinio -> 全局客户端
Nacos ListenConfig -> 配置结构热更新 -> 新逻辑读取新 ViperConf
业务服务 main -> 使用已初始化的 DB/Redis/Kafka/MinIO/Consul client
```

本章要特别区分：配置结构可以热更新，但已经创建的连接池/客户端不一定自动重建。

代码证据：`internal/viper_config_centre.go`

```go
func init() {
    v := viper.New()
    v.SetConfigType("json")
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- 这段代码位于 `init()` 内（`viper_config_centre.go:57`），整个流程在业务 `main()` 之前执行。
- 初始化顺序固定：先 Nacos 拉配置，再依次 `InitRedis/Initdb/InitConsul/InitKafkaProducer/InitAli/InitMinio`（`:162-167`）。
- 任何一个 `Init*` 失败都可能 `panic`（例如 `Initdb` 里 `panic("数据库连接失败")`），服务直接启动失败 —— 所以基础设施不可用时业务代码一行都跑不到。
- 业务服务里不需要也不允许自行创建第二个 DB/Redis client，全部复用 `internal.DB`、`internal.RedisClient` 等全局对象。

## 配置流转

`internal/viper_config_centre.go` 是配置中枢，完整流程分五步：创建 viper 实例 → 组装 Nacos 服务配置 → 注册热更新监听 → 初次拉取配置 → 解析进 `ViperConf`。

第一步，创建 `viper.New()` 并声明 JSON 配置类型；Nacos 地址支持环境变量覆盖，方便本地调试不改源码。

代码证据：`internal/viper_config_centre.go`

```go
func init() {
    v := viper.New()
    v.SetConfigType("json")
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `v.SetConfigType("json")`（`:59`）声明远端内容是 JSON；Viper 支持 `v.ReadConfig(io.Reader)` 从字节流解析，这正是 Nacos 回调数据的对接方式。
- `envOrDefault` / `envIntOrDefault` / `envBoolOrDefault`（`:32-55`）是环境变量覆盖工具：`NACOS_HOST`、`NACOS_PORT`、`NACOS_NAMESPACE`、`NACOS_CONTEXT_PATH`、`NACOS_AUTH_ENABLED`、`NACOS_USERNAME/PASSWORD` 均可覆盖默认值。
- 默认 namespace `ce99961c-0fcf-4f4f-81d6-ac2183f24df1` 与 `scripts/import-nacos-config.sh` 里 `NAMESPACE_ID` 的默认值一致（`import-nacos-config.sh:23`），两处必须对齐，否则服务拉不到配置。
- `serverConfigs`（`:72-79`）是 nacos-sdk 的 `constant.ServerConfig`，指向 Nacos server 本体；后面创建的才是"配置客户端"。

第二步，用 nacos-sdk-v2 创建配置客户端 `clients.NewConfigClient`。开发环境默认不启用鉴权；创建失败只是 `log + return`（不是 panic），但后面的客户端一个都不会初始化。

代码证据：`internal/viper_config_centre.go`

```go
client, err := clients.NewConfigClient(vo.NacosClientParam{
    ClientConfig:  &clientConfig,
    ServerConfigs: serverConfigs,
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `clientConfig`（`:82-97`）设置 `NamespaceId`、`TimeoutMs: 10000`、`NotLoadCacheAtStart: true` 等；开启鉴权时补 `Username/Password`。
- 创建失败直接 `return`：此时 `ViperConf` 保持零值，`InitRedis()` 等也不会执行，服务带着全 nil 的全局客户端继续启动 —— 这是调试时"服务起来了但一调就崩"的常见根源。

第三步，`client.ListenConfig` 注册热更新监听：DataId 是 `clouddisk.json`、Group 是 `dev`，`OnChange` 回调里重新 `ReadConfig + Unmarshal`。

代码证据：`internal/viper_config_centre.go`

```go
// 3. 热更新监听
err = client.ListenConfig(vo.ConfigParam{
    DataId: "clouddisk.json",
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `DataId: "clouddisk.json"`、`Group: "dev"`（`:115-116`）与 `scripts/nacos-config/clouddisk.json` 的导入参数一致（`import-nacos-config.sh:25-26` 的 `DATA_ID/GROUP` 默认值）。
- `OnChange`（`:117-132`）收到新配置后：先 `v.ReadConfig` 读入字节流，再 `v.Unmarshal(&ViperConf)` 覆盖全局结构体 —— 这就是"热更新"的完整实现。
- 注意热更新只更新**配置结构**，不会重建已经创建的 DB/Redis/Kafka/MinIO client，所以"改配置"不等于"连接热切换"（详见"热更新与失败行为"小节）。
- 每个失败分支都有 `Logger.Error` 打点，但都不中断；如果回调里 `Unmarshal` 失败，`ViperConf` 保持旧值，服务继续用旧配置运行。

第四步，初次拉取配置 `client.GetConfig`，同样 `ReadConfig + Unmarshal`，成功后才进入全局客户端初始化。

代码证据：`internal/viper_config_centre.go`

```go
// 4. 初次拉取配置

    DataId: "clouddisk.json",
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
Logger.Info("Nacos config loaded successfully")
```

解释：

- `GetConfig`（`:140-143`）与 `ListenConfig` 使用相同的 DataId/Group；`content == ""` 也被视为失败（`:144`）。
- 初始加载的 `Unmarshal`（`:154-157`）与热更新的 `Unmarshal`（`:128-131`）是同一模式：`v.ReadConfig(io.Reader)` → `v.Unmarshal(&ViperConf)`。
- 只有走到 `Logger.Info("Nacos config loaded successfully")`（`:159`）之后，`ViperConf` 才是可信的；此前任何一步失败都会跳过 `Init*` 序列。

## ViperConfig 结构

`viper_config_centre.go:17` 定义 `ViperConfig`，字段用 `mapstructure` tag 对应 `clouddisk.json` 的键；`var ViperConf ViperConfig`（`:28`）是全局单例，任何服务代码直接读 `internal.ViperConf.Xxx`。

| 配置段 | 结构体 | 用途 |
| --- | --- | --- |
| `redis` | `RedisConfig` | 缓存、JWT 状态、multipart session |
| `mysql` | `MysqlConfig` | 主库连接 |
| `consul` | `ConsulConfig` | 服务注册/发现 |
| `jwt` | `JWTConfig` | 签名密钥、过期策略 |
| `kafka` | `KafkaConfig` | 异步事件总线 |
| `alioss` | `Alioss` | 备用对象存储 |
| `minio` | `MinioConf` | 主对象存储 |
| `clamav` | `ClamAVConfig` | 病毒扫描连接 |

代码证据：`internal/viper_config_centre.go`

```go
type ViperConfig struct {
    RedisConfig  RedisConfig  `mapstructure:"redis"`
    MysqlConfig  MysqlConfig  `mapstructure:"mysql"`
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
var ViperConf ViperConfig
```

解释：

- 每个字段的 `mapstructure` tag 就是 `clouddisk.json` 里的顶层键名；Viper 的 `Unmarshal` 依赖这些 tag 完成 JSON 键 → Go 字段的映射。
- 子结构体同样带 tag，例如 `internal/db.go:20-25` 的 `MysqlConfig{Host,Port,User,Password}` 对应 `mysql.host/port/user/password`。
- `var ViperConf ViperConfig`（`:28`）是包级全局变量，没有用 `sync.Once` 或 getter —— 约定就是"init 完成后所有 goroutine 直接读"。

配置样例与结构体的对应关系，直接看 `scripts/nacos-config/clouddisk.json`。

代码证据：`scripts/nacos-config/clouddisk.json`

```json
{
  "redis":   { "host": "127.0.0.1", "port": "31029" },
  "mysql":   { "host": "127.0.0.1", "port": "30306", "user": "root", "password": "123456" },
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- 这份 JSON 是"写入 Nacos 的原始配置"，也是本地调试的真相来源；改配置 = 改这个文件再跑导入脚本。
- `consul` 段里还嵌套了 `account_srv/file_srv/mcp_srv` 的 host/port —— 对应 `internal/concul.go:24-26` 的 `ConsulConfig` 子结构，业务服务从 `ViperConf.ConsulConfig.AccountSrv.Host` 读取自己的注册地址。
- `minio.port` 是整数（`30900`）而 `redis.port` 是字符串（`"31029"`），与结构体字段类型严格对应：`MinioConf.Port int`（`internal/minio.go:19`）、`RedisConfig.Port string`（`internal/redis.go:12`）—— 类型不匹配时 `Unmarshal` 会失败。

## internal/ 共享包职责

`internal/` 的每个文件基本就是"一个全局变量 + 一个 Init 函数 + 若干封装方法"。所有 `Init*` 都从 `ViperConf` 读配置，业务函数不显式注入 DB/Redis —— 这是本项目的一致性约定，也是调试时最先要确认的环节。

| 文件 | 全局对象/能力 | 说明 |
| --- | --- | --- |
| `db.go` | `var DB *gorm.DB` | MySQL/GORM 主库，`gorm.Open` 初始化（`:18`, `:44`） |
| `redis.go` | `var RedisClient redis.UniversalClient` | 支持单机/哨兵/集群 |
| `kafka.go` | `KafkaProducer` | Sarama 生产者，outbox dispatcher 使用 |
| `minio.go` | `MinIOClient` | 主对象存储能力封装 |
| `ali_oss.go` | `OssClient` | AliOSS 备用/扩展通道 |
| `concul.go` | `ConsulClient` | 服务注册、健康检查、发现 |
| `jwt.go` | token 生成/校验 | account service 签发，gateway filter 校验 |
| `clamav.go` | `ClamAVConfig` 连接 | store service 扫描使用 |
| `Logger.go` | 全局 zap logger | `LoggerWithRID` 带 request id |
| `interceptor.go` | gRPC 拦截器 | `RequestIDUnaryInterceptor` / `RequestIDStreamInterceptor` 从 metadata 提取 `x-request-id` 注入 context |

DB 初始化是最典型的"读 `ViperConf` → 建 client → 失败 panic"模式，注意它先连 MySQL 系统库，自动 `CREATE DATABASE` 再切到业务库，最后逐表 `AutoMigrate`。

代码证据：`internal/db.go`

```go
var DB *gorm.DB

func Initdb() *gorm.DB {
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `var DB *gorm.DB`（`:18`）是包级全局；业务代码直接 `internal.DB.Where(...)`，不做依赖注入。
- 第一步 DSN 不指定库名（`:43-44`），先连 MySQL 系统库并 `CREATE DATABASE IF NOT EXISTS orm_test`（`:50`），再以 `orm_test` 为库名二次 `gorm.Open`（`:58-71`）。
- 失败一律 `panic`（`:45-47`, `:72-74`）—— 数据库连不上，服务直接起不来。
- 建表策略是逐表 `AutoMigrate`（`:76-98`），遇到 `Error 1050`（表已存在）跳过而不是失败，避免老开发库阻塞启动。

Redis 用 `redis.UniversalClient`，一个接口兼容单机/哨兵/集群三种部署；初始化后必须 `Ping` 成功。

代码证据：`internal/redis.go`


解释：

- 注释里保留了单机方案 `redis.Client`，当前选择 `UniversalClient`（`:16`）是为了未来能切哨兵模式（`MasterName` 配置被注释在 `:24-26`）。
- `Ping` 失败 `panic`（`:29-31`）—— Redis 不可用则服务拒绝启动，而不是带病运行。

Kafka 生产者比较特殊：它不 panic，而是最多重试 15 次（每次间隔 2 秒），全部失败才 panic。因为 Kafka 有时比服务启动慢，给一点容错窗口。

## 热更新与失败行为

- `OnChange` 回调把新配置重新 `Unmarshal` 进 `ViperConf`，已初始化 client 是否感知变化取决于各 client 的配置读取时机。
- **Nacos 是硬前置依赖**：配置拉取失败时 `Init*` 序列整体跳过，全局 client 全是 nil，服务带病启动；部分 `Init*`（DB/Redis/MinIO/AliOSS）失败则直接 panic 退出。本地起服务前必须确认 Nacos 可访问且 `clouddisk.json` 已推送。
- 本地配置导入：`scripts/import-nacos-config.sh`；配置样例：`scripts/nacos-config/clouddisk.json`。

先看热更新的真实边界。`OnChange` 只做两件事：读字节流、重新 `Unmarshal`。它不会关闭旧的 DB/Redis 连接，也不会用新地址重连 —— "配置热更新"和"连接热切换"是两回事。

代码证据：`internal/viper_config_centre.go`

```go
OnChange: func(namespace, group, dataId, data string) {
    Logger.Warn("nacos config changed")
    if data == "" {
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
},
```

解释：

- `ViperConf` 会被整体重新赋值（`:128-131`），之后新建的连接（比如新起的服务实例）会用到新配置。
- 但已存在的 `internal.DB`、`internal.RedisClient`、`internal.MinIOClient`、`internal.KafkaProducer` 不会被重建 —— 它们的地址/密码在 init 时已经固化。
- 实际影响面：改 `jwt.signing_key` 这类"每次调用都现读"的配置，热更新立即生效；改 `mysql.host` 这类"只读一次"的配置，热更新不生效，必须重启服务。
- 所以线上改配置后仍建议滚动重启；热更新主要用于 `signing_key` 轮换、限流阈值这类轻量参数。

再看失败行为。Nacos 阶段每一步失败都是 `log + return`，但后果是全局客户端全部未初始化；而 `Init*` 阶段失败是 `panic` —— 两种失败模式要分清。

代码证据：`internal/viper_config_centre.go`

```go
client, err := clients.NewConfigClient(vo.NacosClientParam{...})
if err != nil {
    Logger.Error("create nacos client failed", zap.Error(err))
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `NewConfigClient` 失败（`:108-111`）、`ListenConfig` 失败（`:134-137`）、`GetConfig` 失败或内容为空（`:144-147`）都走 `return`。
- `return` 之后 `InitRedis()` 等一概不执行：`internal.DB` 为 nil，业务第一个 `internal.DB.Where(...)` 就 panic。这类错误日志在 `log/app.log` 里以 "create nacos client failed" / "get initial config failed" 开头，是启动排查的第一搜索词。
- 与之对比，`Initdb`、`InitRedis`、`InitMinio`、`InitAli` 内部失败是 `panic`（如 `db.go:45-47`、`redis.go:29-31`），进程直接退出，日志更醒目。

本地配置导入脚本的职责：把 `clouddisk.json` 直接写进 Nacos 的 MySQL 元数据库（`nacos_config.config_info` 表），绕过 Nacos 3.x 已废弃的旧 HTTP 接口。

代码证据：`scripts/import-nacos-config.sh`

```bash
SET @cfg = FROM_BASE64('${CONFIG_B64}');

INSERT INTO tenant_info (
# ... 省略非关键行，保留完整路径/配置锚点见上文 ...
) ON DUPLICATE KEY UPDATE ...;
```

解释：

- 脚本默认参数与 Go 侧默认值一一对应：`NACOS_SERVER=127.0.0.1:30848`（`:22`）、`NAMESPACE_ID=ce99961c-...`（`:23`）、`DATA_ID=clouddisk.json`（`:25`）、`GROUP=dev`（`:26`）。
- 写 `config_info` 表时同时写 `md5`（`:99` 计算），Nacos 用它做变更对比；`type='json'` 对应 viper 的 `SetConfigType("json")`。
- 执行通道自适应：本机有 `mysql` 客户端就走 local（`:69-76`），否则尝试 `kubectl exec` 进 K8s 里 MySQL Pod（`:77-84`）。
- 导入后默认 `kubectl rollout restart` Nacos deployment（`:177-187`）刷新内存缓存；纯本地 Nacos 则需手动重启。

## 与各服务的关系

- 每个 Go 服务 `main.go` 里都有 `internal` 包的 init 链：配置 -> 全局 client -> gRPC server -> Consul 注册。
- gateway 是 C++ 侧，配置在 `forward_part/gateway/config.json`（含 `port: 38080`），与 Go 侧 Nacos 配置相互独立 —— 改端口要分清改的是哪一侧。

以 `account_srv` 为例看业务服务如何消费这套基础设施：`main()` 里直接读 `internal.ViperConf.ConsulConfig.AccountSrv.Host` 作为注册 IP，`grpc.NewServer` 时挂 `internal.RequestIDUnaryInterceptor()`，注册 Consul 用 `internal.RegisterGrpcService` —— 业务代码自己不碰任何连接细节。

代码证据：`backword_part/account_server/account_srv/main.go`

```go
func main() {
    ip := internal.ViperConf.ConsulConfig.AccountSrv.Host
    // ---- 1. 获取随机端口并监听（只监听一次！）----
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `internal.ViperConf.ConsulConfig.AccountSrv.Host`（`:35`）读的是 Nacos 配置里 `consul.account_srv.host` —— 注册 IP 也来自配置中心，而不是硬编码。
- `ListenAutoPort`（`:25-32`）监听随机空闲端口，然后把这个随机端口注册进 Consul —— gateway 通过服务发现拿到"IP + 随机端口"。
- `internal.RequestIDUnaryInterceptor()`（`:45`）来自 `internal/interceptor.go`，配合日志打点形成全链路 request id。
- `internal.RegisterGrpcService("account_srv", "account_srv_1", ...)`（`:55-59`）和 `internal.RegisterGRPCHealth`（`:52`）都来自 `internal/concul.go`，即 06 章表格里的共享能力。
- 每个服务大致是同一模板：`ListenAutoPort()` → `grpc.NewServer()` → register service → Consul 注册 → `Serve()` → `ElegantExit()`（`:16-22` 优雅退出时 `internal.DeregisterService` 注销 Consul）。

## 状态转换

```text
进程启动 -> Nacos 配置读取成功 -> ViperConf 初始化 -> global clients 初始化 -> 服务 main 可运行
Nacos 配置变更 -> ListenConfig 回调 -> ViperConf 更新 -> 后续读取配置看到新值
配置缺失/格式错误 -> init panic 或 client 初始化失败 -> 服务无法启动
配置更新但连接参数变化 -> ViperConf 已变 -> 旧 DB/Redis/Kafka/MinIO client 仍可能保持旧连接
```

这解释了为什么改 Nacos 配置后，有些变化需要重启服务才能完全生效。

## 关键数据结构 / 字段

- `ViperConf`：所有 Go 服务共享的配置落点。
- `NacosConfig`：配置中心地址、namespace、data id/group 等读取参数。
- `DB / RedisClient / KafkaProducer / MinIOClient / ConsulClient / OssClient`：internal 包全局客户端。
- `ListenConfig callback`：配置热更新入口。
- `ClamAV config`：store service 扫描链路的外部依赖配置。

## 常见误判与排障顺序

- 误判：热更新会重建所有连接。正确理解：源码主要更新配置结构，连接池是否重建要看具体实现。
- 误判：业务服务 main 里没初始化 DB。正确理解：`internal` 包 init 已隐式初始化。
- 误判：基础设施错误是业务逻辑错误。正确理解：先查 Nacos 配置和 global client 初始化。
- 排障顺序：Nacos 地址/namespace -> clouddisk.json 内容 -> ViperConf 解析 -> 各 Init* 函数 -> 服务 main 使用点。
