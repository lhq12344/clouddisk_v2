# 15. 前端 API 和状态：UI 如何驱动后端能力

## 本章定位

前端不是纯展示层，而是后端能力的第一驱动者：它保存 JWT（`localStorage('oss_token')`）、统一封装 API 调用（token/request-id 注入）、计算文件 SHA-256 hash、维护上传任务状态机、判断文件是否可预览/下载，并在 multipart 上传中把 session 存进浏览器以便断点恢复。

## 总链路

前端把用户操作编排成后端能力调用：

```text
登录：AuthPage -> ApiService.signin -> localStorage oss_token -> request() 注入 Authorization
文件列表：App.fetchFiles -> api.queryFiles -> FileItem[] -> pending_scan 轮询
... 省略非关键行，完整证据见上文路径/锚点 ...
文本编辑：preview fetch -> editContent -> sha256Hex -> simpleUpload 新内容
```

这说明前端是状态编排层：它不直接访问 MySQL/Kafka/ClamAV，但要理解后端状态并驱动正确 API 顺序。

应用的挂载点逻辑在 `App.tsx`：未登录时渲染 `AuthPage`，登录成功后渲染文件列表 + `UploadManager`；所有 HTTP 出入都经过 `services/api.ts` 的 `ApiService` 单例。

代码证据：`forward_part/static/App.tsx`（认证 gate，L322-324）

```tsx
if (!isAuthenticated) {
  return <AuthPage onSuccess={() => setIsAuthenticated(true)} theme={theme} />;
}
```

代码证据：`forward_part/static/services/api.ts`（单例导出，L278）

```ts
export const api = new ApiService();
```

解释：

- `isAuthenticated` 初值来自 `localStorage.getItem('oss_token')` 是否存在（App.tsx L133），刷新页面后保持登录态。
- `api` 是模块级单例，所有组件（AuthPage/UploadManager/App）共享同一份 token 读取与请求封装逻辑。
- 登录态切换由 `onSuccess` 回调驱动：AuthPage 调 `api.signin` 成功 → App 置 `isAuthenticated=true` → 触发首次 `fetchFiles/fetchUserInfo`。

## ApiService

`ApiService` 是所有 HTTP 的统一入口。核心是私有方法 `request()`：它从 `localStorage('oss_token')` 取 token 注入 `Authorization` 头，给每个请求生成 `X-Request-Id`（用于全链路日志关联，网关和 Go 服务都透传它），并按 HTTP 状态码把错误归一成 `ApiError`。

代码证据：`forward_part/static/services/api.ts`（request 统一封装，L64-113 节选）

```ts
private async request(endpoint: string, options: RequestInit = {}) {
  const token = this.getToken();
// ... 省略非关键行，完整证据见上文路径/函数锚点 ...
}
```

token 的生命周期被严格管理：`signin` 成功后写入 `oss_token`；`logout` 先把 token 加入服务端黑名单，再清 token 和所有 multipart 会话（localStorage + sessionStorage 两个存储都扫一遍 `multipart_upload_sessions` 前缀的 key）。

代码证据：`forward_part/static/services/api.ts`（signin 与 logout，L119-148）

```ts
async signin(data: any) {
  const res = await this.request('/user/signin', { method: 'POST', body: JSON.stringify(data) });
// ... 省略非关键行，完整证据见上文路径/函数锚点 ...
}
```

文件 API 家族一一对应网关路由（`/file/query|download|showfile|delete|upload|initupload|PresignParts|uploadpart|CompleteMultipart|AbortMultipart|Status`）。`simpleUpload` 直接把文件 Blob 作为 body 上传，元信息走自定义头；`uploadPresignedPart` 则按 URL 是回环地址还是 MinIO 地址走两条路径。

代码证据：`forward_part/static/services/api.ts`（simpleUpload 与 uploadPresignedPart，L187-198、L214-253 节选）

```ts
async simpleUpload(file: Blob, filename: string, fileHash: string, contentType?: string): Promise<UploadResponse> {
  return this.request('/file/upload', {
// ... 省略非关键行，完整证据见上文路径/函数锚点 ...
}
```

解释：

- `request()` 是所有 API 的唯一 fetch 出口：token 注入、request-id、Content-Type 兜底、JSON 解析、错误归一全在这里，业务方法只写 `endpoint + body`。
- `X-Request-Id` 用 `crypto.randomUUID()` 生成，贯穿 网关 → file_srv → Kafka 消息头 → store_srv 日志（`extractKafkaRequestID`），是全链路排障的主键。
- `simpleUpload` 复用普通 JSON 请求通道但 body 是原始文件（多部分语义被自定义头取代），网关侧 `LoadFile` 从 headers 取文件名/hash/size。
- `uploadPresignedPart` 的双路径：URL 指向 `127.0.0.1`/`localhost`（MinIO NodePort 暴露在回环地址时浏览器拿不到）就走 `/file/uploadpart` 让网关代理 PUT（URL 放在 `X-Presigned-Part-Url` 头）；否则浏览器直连 MinIO 预签名 URL 并回读 ETag。
- 服务端返回的 `code` 不是 HTTP 状态时（例如下载 URL 放在 `Resp.code=0` 的 message 里），由上层按业务字段判断，`request()` 只负责传输层。

## UploadManager

`UploadManager` 同时处理小文件和大文件：先对文件内容算 SHA-256（`crypto.subtle.digest`），按 5MB 阈值分流——小文件走 `api.simpleUpload`，大文件走 multipart 全流程。每个文件对应一个 `UploadTask`，UI 用任务状态 + 进度条实时渲染。

上传完成后任务可能停留在 `pending_scan`（病毒扫描未结束）。`UploadManager` 对这类任务启动 3 秒轮询 `api.queryFiles()`，用 `filehash → status` 映射刷新任务状态，扫描结束自动从 amber 变绿/变红。

代码证据：`forward_part/static/components/UploadManager.tsx`（pending_scan 轮询，L282-306）

```tsx
useEffect(() => {
  const pendingTasks = tasks.filter((t) => t.status === 'pending_scan' && t.fileHash);
// ... 省略非关键行，完整证据见上文路径/函数锚点 ...
}, [tasks]);
```

解释：

- hash 计算是同步阻塞的（`await file.arrayBuffer()` 把整个文件读进内存），所以先置 `status='uploading', detail='hashing'` 提示用户；这也是大文件 hash 成本的体现——但它是服务端去重的必要条件。
- 断点恢复的关键不在本地 session，而在服务端：`getMultipartStatus` 返回 `uploaded_parts`，本地 session 过期或丢失时（Init 返回 `status != 'init'`，见 `buildMultipartSession`）重新 Init 即可，已传 part 不会重复传。
- `PART_PARALLELISM=2` 控制并发；`uploadPresignedPart` 的 ETag 返回值在此流程中不强制收集——complete 时服务端会自己 `ListObjectParts` 取 ETag。
- 上传失败时 `uploadResponseFromError` 从 `ApiError.body` 里还原 `status/object_key/file_hash`——例如服务端命中已感染文件时返回的 `blocked by virus scan` 会直接反映到任务状态。
- `toTaskStatus` 把服务端状态原样映射为任务状态，因此任务面板能看到 `success/pending_scan/infected/scan_failed` 全谱系。

## 状态转换

前端有两类状态：认证状态和文件/上传任务状态。

```text
未登录 -> signin 成功 -> localStorage 保存 token -> isAuthenticated=true
已登录 -> logout -> revoke/logout API + 清 token + 清 multipart session -> isAuthenticated=false
```

上传任务状态：

```text
queued -> hashing -> uploading -> pending_scan -> success/infected/scan_failed
queued/hashing/uploading -> 异常 -> error
multipart initialized -> partial uploaded -> resumed by status -> completed -> pending_scan
```

文件列表状态：

```text
pending_scan -> 轮询 queryFiles -> success -> 按钮开放
pending_scan -> 轮询 queryFiles -> infected/scan_failed -> 展示阻断/失败原因
```

## 关键数据结构 / 字段

- `FileItem`：文件列表行，驱动下载/预览按钮、状态标签和 scan_detail 展示。
- `UploadTask`：上传任务面板状态，记录 progress/status/error/detail。
- `MultipartSession`：本地恢复入口，保存 upload_id、part_size、total_parts。
- `MultipartInitResponse`：服务端分片会话初始化结果。
- `ApiErrorBody`：兼容 Gateway/Go 服务不同错误 JSON 形态。
- `oss_token`：JWT 本地存储 key，是前端身份态的核心。

## 常见误判与排障顺序

- 误判：前端只展示后端结果。正确理解：前端负责任务状态机、断点恢复、轮询收敛和 URL rewrite。
- 误判：localStorage multipart session 是可信进度。正确理解：它只保存 upload_id，已传分片以服务端 status 为准。
- 误判：pending_scan 是失败。正确理解：它是异步扫描中的正常状态。
- 排障顺序：token 是否存在 -> request headers 是否正确 -> API 返回 body -> UploadTask 状态 -> queryFiles 轮询 -> URL rewrite/浏览器访问。
