# 14. 对象存储层：MinIO 与 AliOSS

## 本章定位

对象存储保存文件内容（对象本体），MySQL 保存元数据和关系（File/UserFile 表）。当前主链路以 MinIO 为主：小文件上传、multipart、下载、病毒扫描读取全部围绕 `internal.MinIOClient` 展开。AliOSS 在 `internal/ali_oss.go` 里有完整 client 封装，但全代码库没有任何业务调用点，学习时应把它视为扩展/备用实现，不是当前主路径。

## 总链路

对象存储层在不同业务场景里的位置不同：

```text
小文件上传：file_srv.UploadFile -> MinIOUploadStream(PutObject) -> File/UserFile -> Outbox scan
分片上传：InitMultipart -> MinIOMultipartInit -> PresignParts -> PUT part -> ListParts -> CompleteMultipart
下载/预览：file_srv owner/status 校验 -> MinIOPresignGetURLWithParams -> browser download/preview/fetch
病毒扫描：store_srv -> MinIOGetObjectStream -> ClamAV -> success/infected/scan_failed
备用扩展：AliOSS client 已封装，但当前主链路没有业务调用点
```

这条链路说明：MinIO 是当前文件字节主存储；MySQL 只保存元数据和状态；AliOSS 是可扩展实现，不是当前上传/下载/扫描主链路。

`internal/minio.go` 的全局入口是 `MinIOClient`（`MINIOClient` 结构体 = 原始 minio-go client + bucket 名），由 `InitMinio()` 在配置加载阶段创建。

## Object Key

`backword_part/file_server/file_srv/protobuf/file.go` 的 `buildObjectKey(fileHash)` 生成 `files/<hash>` 形式的 key。key 由内容 hash 决定，不包含用户文件名，所以相同内容的文件（不同用户、不同文件名）会命中同一个对象——这是整个去重设计的基础。

代码证据：`backword_part/file_server/file_srv/protobuf/file.go`（buildObjectKey，L57-59）

```go
func buildObjectKey(fileHash string) string {
	return fmt.Sprintf("files/%s", strings.TrimSpace(fileHash))
}
```

读取侧（下载/预览/扫描）不直接信任数据库里存的 key，而是通过 `resolveStoredObjectKey` 统一解析：优先用 `file.ObjectKey`，为空时用 `sha1` 重新构造。

代码证据：`backword_part/file_server/file_srv/protobuf/file.go`（resolveStoredObjectKey，L448-459）

```go
func resolveStoredObjectKey(file *model.File) string {
	if file == nil {
		return ""
// ... 省略非关键行，保留完整路径/函数锚点见上文 ...
}
```

解释：

- `files/` 前缀是对象命名空间，避免与其它用途的对象混在一起；store service 的 `normalizeObjectKey` 在事件 payload 缺 key 时也用同样的 `"files/" + sha1` 兜底（`other_srv/store_srv/kafka/kafkacunsumer.go`）。
- 同一个 hash 只产生一个对象，但 MySQL 里可以有多个 `UserFile` 行指向同一个 `File` 行——对象层去重，元数据层多对一。
- `buildObjectKey` 的入参是 `fileHash`（sha1），不是用户上传时的原始文件名，所以"重命名文件"不会产生新对象。

## 小文件路径

小文件上传在 `UploadFile`（gRPC client-streaming）里把 stream 接到 MinIO 上传：第一个消息必须是 `meta`，后续消息是 `data` 块。服务端不先把数据攒在内存/磁盘，而是用 `io.Pipe` 把 goroutine 里的 `MinIOUploadStream` 与主循环里的 `stream.Recv()` 对接起来，边收边传。

代码证据：`backword_part/file_server/file_srv/protobuf/file.go`（UploadFile 主流程，L688-705）


解释：

- `meta.FileSize` 必须与 `written` 一致，防的是客户端谎报大小导致的元数据错位。
- UserMetadata（`x-file-name` 等）随对象存储，store service 扫描后回填元数据时也可参考。
- 该路径在 `file.go:634` 之前还有一条去重分支：hash 已存在时直接 `drainUploadFileStream` 丢弃数据流并复用已有对象，不产生第二次上传。

## 分片路径

multipart 的控制面全部是普通 gRPC RPC：`InitMultipart` 先算出分片方案并创建 MinIO upload id，然后把整个会话的元信息存进 Redis（key = `metaKey(uploadID)`）；前端随后用 `PresignParts` 拿预签名 PUT URL 直传各 part；`CompleteMultipart` 校验 part 齐全后合并对象并落库。

`InitMultipart` 用 `minio.OptimalPartInfo` 计算 part size，然后生成两层 upload id：`uploadID` 是 file service 自己生成的会话 id（`genUploadID`，存 Redis），`ossUploadID` 是 MinIO 侧真正的 upload id（存进 Redis 的 `oss_upload_id` 字段）。

代码证据：`backword_part/file_server/file_srv/protobuf/file.go`（InitMultipart，L993-1014）


- gRPC 流式 `UploadPart` 已经是 `codes.Unimplemented`（file.go L1089-1091），真实主链路是 `PresignParts + 直传 MinIO`。

```go
Logger.Info("All services initialized")
```

解释：

- `OssClient` 是"能跑但没有被调用"的封装：全代码库（`backword_part/`、`other_srv/`、`internal/`）只有 `ali_oss.go` 自身和 `viper_config_centre.go` 的 `InitAli()` 提到它，没有任何上传/下载/扫描路径调用 `OssClient` 方法。
- `UploadFile` 的 checkpoint 参数（`./checkpoint`）是 OSS SDK 的断点续传持久化，适合把本地大文件搬运到 OSS 的运维场景，不是浏览器上传链路的组件。
- 结论：学习时把 `ali_oss.go` 当作"对象存储抽象的第二实现模板"即可；当前 09/11/13 章描述的主链路全部围绕 `MinIOClient`。

## 状态与边界转换

对象存储自身不维护业务状态，业务状态由 file service 和 store service 写 MySQL；MinIO 只提供对象事实。

```text
PutObject 成功 -> object stored -> MySQL File.status=pending_scan
Multipart complete 成功 -> object merged -> MySQL File.status=pending_scan
Presigned GET 生成 -> 临时 URL 可访问 -> 过期后需要重新向 file service 申请
... 省略非关键行，保留完整路径/锚点见上文 ...
扫描失败 -> object 可能仍存在 -> File.status=scan_failed，禁止签下载/预览 URL
```

边界要点：MinIO 不知道用户是谁，也不知道文件是否安全；用户归属和安全门禁都在 MySQL/Gateway/file service/store service 中完成。

## 关键数据结构 / 字段

- `object_key`：MinIO 对象地址，通常由 hash 构造成 `files/<hash>`。
- `bucket`：MinIOClient 持有的存储桶名，由 Nacos/Viper 配置初始化。
- `userMeta`：上传对象时写入的辅助 metadata，如文件名、hash、user id。
- `upload_id / oss_upload_id`：multipart 业务会话 id 与 MinIO 原始 upload id 的分离。
- `ETag / PartNumber`：multipart complete 所需的对象存储事实。
- `File.status`：不在 MinIO 内，由 MySQL 保存，是下载/预览门禁。

## 常见误判与排障顺序

- 误判：对象存储保存业务权限。正确理解：MinIO 只保存字节，权限由业务服务签 URL 前校验。
- 误判：文件名就是 object key。正确理解：object key 基于 hash，文件名在 `UserFile` 关系里。
- 误判：AliOSS 是当前主链路。正确理解：当前上传、multipart、下载、扫描证据都指向 `MinIOClient`。
- 排障顺序：Nacos MinIO 配置 -> `InitMinio` 是否成功 -> bucket 是否存在 -> object_key 是否正确 -> Put/Get/ListParts/Complete 是否成功 -> MySQL 状态是否同步。

## 阅读检查

- 能说明 object key 为什么基于 hash（`files/<hash>`），以及相同 hash 复用对象时元数据层如何多对一。
- 能区分元数据 DB（File/UserFile 表）和对象存储（MinIO bucket）各自的职责与一致性问题（先传对象、后落库、失败删对象）。
- 能列出 MinIO 在小文件（PutObject + pipe 流式）、分片（Core 系 multipart 原语）、下载（预签名 GET + content-disposition）、扫描（GetObject stream → ClamAV INSTREAM）中的不同 API 角色。
- 能解释 multipart 会话的两层 upload id 与 Redis 状态机，以及 `ensureMultipartOwner` 为什么必要。
- 能指出 `UploadPart` gRPC 流式接口已废弃，真实主链路是 `PresignParts + 预签名 PUT 直传`。
- 能说明为什么只有 `success` 状态的文件才能拿到下载/预览签名 URL，以及 URL 为什么只有 10 分钟有效期。
- 能说出 AliOSS 与 MinIO 的实际地位差异：AliOSS 有完整封装但无业务调用点，MinIO 是唯一主链路。
