# CloudDisk V2 源码复核版学习文档

> 目的：重新学习这个网盘项目时，不从抽象介绍入手，而是按当前仓库源码证据建立一条“从网关到服务、从同步请求到异步中间件”的阅读路线。
>
> 证据口径：本文所有关键结论尽量绑定到仓库文件路径、函数名、结构体字段或配置项。行号来自本次扫描时的当前工作树。

## 3. 架构全景图 High-Level Architecture

### 3.1 分层架构图

```text
React 前端
  forward_part/static
  - services/api.ts 生成 HTTP 请求、JWT Authorization、X-Request-Id
  - components/AuthPage.tsx / UploadManager.tsx 触发登录、上传、分片上传

接入层 OpenResty
  forward_part/config/nginx/nginx.conf
  - :2024 主 HTTP 入口，转发 API 到 cloudisk_backend
  - :2025 preview/download 静态文件入口
  - CORS、X-Request-Id、上传流式代理开关

C++ Gateway / Drogon
  forward_part/gateway/main.cc
  - 监听 0.0.0.0:38080
  - 注册到 Consul
  - Redis 客户端、JWT signing key、Kafka 地址放入 MyAppData
  - AccountController / FileController / AIController 把 HTTP 转为 gRPC

Go gRPC 业务服务
  backword_part/account_server/account_srv
  - account_srv: 登录、注册、邮箱验证、用户信息

  backword_part/file_server/file_srv
  - file_srv: 文件元数据、小文件流式上传、下载预签名 URL、分片上传、删除、Outbox dispatcher

  backword_part/AI_server
  - AI_srv: 文件 AI 请求处理

  backword_part/mcp_server
  - mcp_server: MCP 工具服务与 API key 管理

异步服务
  other_srv/store_srv
  - 消费 file.upload.cmd，执行 MinIO 对象读取、ClamAV 扫描、文件状态落库、DLQ

  other_srv/email_srv
  - C++ Kafka consumer，消费邮件任务并调用邮件服务

基础设施层
  Nacos: clouddisk.json 配置中心
  Consul: 服务注册 / 发现 / 健康检查
  MySQL: GORM 持久化用户、文件、outbox、inbox、DLQ、MCP API key
  Redis: pending registration、multipart upload session、JWT 黑白名单相关状态
  Kafka: outbox 投递与异步文件扫描、邮件任务
  MinIO / AliOSS: 对象存储；当前主链路实际大量使用 MinIO
  ClamAV: store_srv 读取对象后做病毒扫描
```

### 3.4 数据流向

#### 登录链路

```text
AuthPage.handleSubmit
  -> api.signin('/user/signin')
  -> OpenResty /user/signin
  -> AccountController::signin
  -> accountService.Signin gRPC
  -> account_srv 查询 Account + 校验密码 + 生成 JWT
  -> gateway 把 token 作为 JSON 返回
  -> frontend localStorage('oss_token')
```

证据：`forward_part/static/components/AuthPage.tsx:28` 调 `api.signin`；`forward_part/static/services/api.ts:119` 保存 `oss_token`；`forward_part/config/nginx/nginx.conf:87` 代理 `/user/signin`；`forward_part/gateway/controllers/AccountController.h:31` 路由；`backword_part/account_server/account_srv/protobuf/account.go:31` 查询用户；`account.go:45` 校验密码；`account.go:58` 生成 JWT。

#### 小文件上传链路

```text
UploadManager
  -> api.simpleUpload('/file/upload')，header 带 X-File-Name/X-File-Hash/X-File-Size
  -> OpenResty /file/upload，关闭 proxy buffering
  -> FileController::LoadFile，JWT 取 userId
  -> file_srv UploadFile(stream)
  -> MinIOUploadStream 写对象
  -> upsert File/UserFile
  -> enqueueScanRequested 写 Outbox
  -> OutboxDispatcher 发 Kafka
  -> store_srv 消费并 ClamAV 扫描
  -> 更新 File.status = success / infected / scan_failed
```

证据：`forward_part/static/services/api.ts:187` 小文件上传；`nginx.conf:136` `/file/upload`；`FileController.h:32` 路由；`file.go:632` gRPC stream 收 meta；`file.go:686` object key；`file.go:690` MinIOUploadStream；`file.go:746` upsert；`file.go:225` enqueueScanRequested；`kafkaproduct.go:43` dispatcher；`kafkacunsumer.go:273` 扫描；`kafkacunsumer.go:325` clean 落库。

#### 分片上传链路

```text
api.initMultipart('/file/initupload')
  -> file_srv InitMultipart
  -> MinIO Core.NewMultipartUpload
  -> Redis HSet mp:meta:<upload_id>

api.presignParts('/file/PresignParts')
  -> file_srv PresignParts
  -> Redis HMGet session
  -> MinIOPresignMultipartPutURL

api.uploadPresignedPart
  -> 直传 MinIO URL；如果 URL 是 localhost/127.0.0.1，则走 /file/uploadpart 代理

api.completeMultipart('/file/CompleteMultipart')
  -> file_srv CompleteMultipart
  -> listUploadedParts
  -> MinIOMultipartComplete
  -> upsert File/UserFile + Outbox
  -> Redis 标记 completed
```

证据：`forward_part/static/services/api.ts:200` init；`api.ts:207` presign；`api.ts:214` uploadPresignedPart；`api.ts:256` complete；`file.go:955` InitMultipart；`file.go:1003` uploadID；`file.go:1005` MinIOMultipartInit；`file.go:1014` Redis HSet；`file.go:1044` PresignParts；`file.go:1091` CompleteMultipart；`file.go:1145` MinIOMultipartComplete；`file.go:1161` Redis completed。

#### 下载 / 预览 / 删除链路

下载和预览通过 gateway 调 file_srv 查用户文件关系和对象状态，返回 MinIO 预签名 GET URL；删除先删 `UserFile` 关系，如果没有剩余引用再删 `File` 与 MinIO object。

证据：`forward_part/static/services/api.ts:154` download；`api.ts:176` preview；`api.ts:166` delete；`forward_part/gateway/controllers/FileController.h:31` download；`FileController.h:33` showfile；`FileController.h:34` delete；`backword_part/file_server/file_srv/protobuf/file.go:89` buildPresignedGetURL；`file.go:806` DeleteFile；`file.go:839` 事务内删关系/文件；`file.go:858` 删除 MinIO object。

### 3.5 控制反转与依赖关系

这个项目不是 Spring 式容器，主要是“全局初始化 + 显式注册 + generated interface 实现”。Go 侧 `internal/viper_config_centre.go:init()` 拉 Nacos 配置后初始化 Redis、DB、Consul、Kafka、AliOSS、MinIO，全局变量被业务服务直接引用；各 gRPC `main.go` 创建 server 后把实现注册进 generated service interface。C++ gateway 侧由 Drogon 扫描 controller 路由，启动前读取配置并把 Redis、Kafka、JWT、Consul 注册对象放到应用上下文或单例中。

证据：`internal/viper_config_centre.go:159` 初始化顺序；`backword_part/file_server/file_srv/main.go:56` grpc.NewServer；`file_srv/main.go:64` RegisterFileServiceServer；`forward_part/gateway/main.cc:42` Drogon beginning advice；`forward_part/gateway/main.cc:48` 写入 `MyAppData`。

### 4.3 生命周期

#### 用户注册生命周期

1. `Signup` 检查用户名是否已存在。
2. 用 `go-password-encoder` 生成 salt/hash。
3. 写 Redis `pending_reg:<email>`，TTL 10 分钟。
4. `VerifyCode` 读取 pending data，创建 `Account`。
5. 删除 pending key。

证据：`account.go:70`、`account.go:83`、`account.go:93`、`account.go:110`、`account.go:128`、`account.go:134`。

#### 文件对象生命周期

1. 上传对象到 MinIO。
2. DB 创建/复用 `File`，初始状态 `pending_scan`。
3. DB 创建/恢复 `UserFile` 关系。
4. 写 Outbox `FILE_SCAN_REQUESTED`。
5. Outbox dispatcher 发 Kafka。
6. store_srv 消费，ClamAV 扫描。
7. clean 则 `File.status=success`；infected 则删除对象并 `File.status=infected`；终端失败则 `scan_failed` + DLQ。

证据：`file.go:690`、`file.go:273`、`file.go:166`、`file.go:225`、`kafkaproduct.go:43`、`kafkacunsumer.go:273`、`kafkacunsumer.go:325`、`kafkacunsumer.go:342`、`kafkacunsumer.go:172`。

## 9. 遇到的坑与笔记 Pitfalls & Notes

### 9.1 Nacos 是服务启动的前置依赖

Go 包的 `init()` 会直接创建 Nacos client、监听配置、拉 `clouddisk.json`、初始化所有基础设施 client。若 Nacos 不可用，`ViperConf` 可能为空，后续服务注册、DB、Redis、Kafka、MinIO 都会连带失败。证据：`internal/viper_config_centre.go:57`、`:103`、`:137`、`:159`。

### 9.2 全局 client 隐式依赖较重

业务函数直接引用 `internal.DB`、`internal.RedisClient`、`internal.MinIOClient`、`internal.KafkaProducer`。学习时要先看 `internal/` 初始化，否则直接读业务函数会不知道依赖从哪里来。证据：`account.go:34`、`file.go:134`、`file.go:690`、`kafkaproduct.go:161`。

### 9.3 Outbox 成功发 Kafka 后不能回滚

`OutboxDispatcher.workerLoop` 注释明确说明：Kafka 已发送但 `markSent` 更新失败时，不能回滚 Kafka，只能依赖消费端 inbox 幂等。证据：`backword_part/file_server/file_srv/kafkaproduct.go:101`。

### 9.4 Inbox 是消费端幂等核心

store_srv 处理消息前 `tryBeginInbox` 创建/抢占 `Inbox`；如果已 `DONE` 则跳过，如果锁被别的实例持有则返回 `ErrInboxLocked`。证据：`other_srv/store_srv/kafka/kafkacunsumer.go:248`、`:439`、`:461`、`:500`。

### 9.5 文件上传后不是立即可下载

新文件默认 `pending_scan`，store_srv 扫描成功后才变 `success`。删除和查询逻辑也会检查 `File.Status`。证据：`model/filedb.go:9`；`file.go:277` 创建 pending_scan；`file.go:829` 删除前检查 pending scan；`kafkacunsumer.go:325` clean 后 success。

### 9.6 分片上传当前实际走“预签名直传”，gRPC UploadPart 已废弃

`UploadPart` gRPC 方法还在 proto 里，但 Go 实现直接返回 Unimplemented，提示使用 `PresignParts + direct multipart upload`。证据：`proto/file_srv/file.proto:181`；`backword_part/file_server/file_srv/protobuf/file.go:1087`。

### 9.7 用户身份以 JWT 注入为准，multipart 会校验 owner

Gateway 从 JWT attributes 拿 `Name` / `ID`，file_srv 的 multipart 函数通过 gRPC metadata 中的 `x-user-id` 做 owner 校验。证据：`FileController.cc:18`；`file.go:143`；`file.go:155`。

### 9.8 OpenResty 当前 upstream 是固定本地 Gateway，不是真正 Lua 动态 upstream

虽然存在 `lua_shared_dict consul_services` 和 Lua 文件，但 `nginx.conf` 当前 `upstream cloudisk_backend` 固定到 `127.0.0.1:38080`，注释说明本地开发环境避免依赖镜像内缺失的 `lua-resty-http`。证据：`forward_part/config/nginx/nginx.conf:36`、`:39`、`:40`；Lua 文件存在于 `forward_part/config/nginx/lua/`。

### 9.9 C++ 构建依赖容易卡环境

Gateway 的 CMake 对 `librdkafka++` 缺失直接 `FATAL_ERROR`；email_srv 对 `librdkafka` 和 `hiredis` 缺失也直接失败。证据：`forward_part/gateway/CMakeLists.txt:81`、`:84`；`other_srv/email_srv/CMakeLists.txt:44`、`:60`。

### 9.10 文件名和内容哈希要区分

`File.Sha1` 是内容哈希，`UserFile.Name` 是用户视角文件名；下载/删除通常需要通过用户关系表确认权限。证据：`model/filedb.go:16`、`:28`；`file.go:817` 删除时查 `UserFile` 并 preload `File`。
