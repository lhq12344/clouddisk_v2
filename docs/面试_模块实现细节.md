# CloudDisk V2 — 各模块实现细节（面试用）

## 整体架构

```
Client → OpenResty (:2024) → C++ Gateway (Drogon) → Go gRPC 微服务
                                ├── account_srv — 注册/登录/JWT
                                ├── file_srv    — 文件上传/下载/预览/删除（直传 MinIO）
                                ├── AI_srv      — AI 能力调用
                                └── mcp_server  — MCP 工具服务

file_srv → Outbox(Kafka FILE_SCAN_REQUESTED) → store_srv（消费 + Inbox 抢占 + ClamAV 扫描）→ 更新文件状态
email_srv (C++) ← Kafka — 邮件通知

基础设施：Nacos(配置中心) + Consul(服务发现) + Kafka(异步扫描事件) + MySQL + Redis + MinIO/AliOSS
部署：Kubernetes
```

### 重构前后对比

| 维度       | 旧架构                                        | 新架构                                                 |
| ---------- | --------------------------------------------- | ------------------------------------------------------ |
| 小文件上传 | DB+Outbox → Kafka → store_srv → MinIO（异步） | 流式 Pipe → MinIO（同步直传）                          |
| 大文件上传 | 流式 gRPC → file_srv → MinIO（服务端中转）    | Presigned URL → 浏览器直传 MinIO                       |
| Kafka 角色 | 文件上传通道                                  | 扫描事件通知（仅 FILE_SCAN_REQUESTED）                 |
| 状态机     | pending → success                             | pending_scan → 病毒扫描 → success/infected/scan_failed |

## 二、C++ Gateway（Drogon 框架）

### 2.1 职责


### 2.3 JWT 鉴权机制

**Token 生命周期管理（Redis）：**

```
签发时：
  ZADD jwt:whitelist:user:{userId} {timestamp} {token}
  ZCARD 检查数量，超过 2 个时 ZPOPMIN 移除最旧的
  被移除的 token SADD 到 jwt:blacklist

验证时（jwt_decode 过滤器）：
  从 Authorization: Bearer {token} 提取 token
  HS256 解码，验证 issuer == "Signin"
  SISMEMBER jwt:blacklist 检查是否已注销
  ZSCORE jwt:whitelist:user:{userId} 检查是否在白名单
  通过后将 ID、Name 存入请求 attributes

登出时：
  从白名单 ZREM 移除
  SADD 加入黑名单
```

### 2.4 流式上传代理（UploadFileProxy）

小文件走 `/file/upload` → Gateway 代理到 file_srv 的 `UploadFile` 流式 gRPC：

```cpp
// UploadFileProxy 收集 HTTP 请求体分块
// 通过独立线程 + mutex/deque 安全地 buffer 数据
// 转换后转发到 gRPC UploadFile 流（first=meta, following=data）
class UploadFileProxy : public std::enable_shared_from_this<UploadFileProxy> {
    void run() {
        auto writer = stub_->UploadFile(&context, &grpcResp);
        // 第一条：发送 meta
        writer->Write(metaReq);
        // 后续：逐条发送 data chunk
        for (chunk : chunks_) {
            writer->Write(dataReq);
        }
        writer->WritesDone();
        writer->Finish();  // 获取 gRPC 最终状态
    }
};
```

### 2.5 ARC 缓存（自适应替换缓存）

**用途：** 缓存 Consul 服务发现结果（gRPC 连接 + Stub），容量 20。

**算法实现：**

- LRU + LFU 混合缓存，自适应分区
- LRU 部分：双向链表，按访问时间排序
- LFU 部分：频率映射 `map<size_t, list<NodePtr>>`，追踪最小频率
- Ghost Cache：记录被淘汰的 key，命中时动态调整 LRU/LFU 容量比例
- 访问次数超过阈值（2次）时，从 LRU 提升到 LFU

## 三、Account 服务（Go gRPC）

### 3.1 启动流程

```
1. net.Listen("tcp", ":0") 动态获取可用端口
2. 创建 gRPC Server，注册 AccountService
3. 注册 gRPC Health Check（供 Consul 探活）
4. 注册到 Consul（account_srv_1）
5. 启动 Serve
6. 监听 SIGINT/SIGTERM，优雅退出时从 Consul 注销
```

### 3.2 注册流程（Signup）

```
1. 查询 username 是否已存在（Name 字段有唯一索引）
2. 密码加密：
   - 库：go-password-encoder（PBKDF2）
   - 参数：SaltLen=16, Iterations=100, KeyLen=32, HashFunction=MD5
   - 生成 salt + encodedPassword（均为 base64）
3. 创建 Account 记录（salt、password、username、email）
4. 返回 code=0 表示成功
```

### 3.3 登录流程（Signin）

```
1. 按 username 查询 Account
2. password.Verify(输入密码, 存储的salt, 存储的hash, options)
3. 生成 JWT Token：
   - 算法：HS256
   - Claims：ID(用户ID), Name(用户名), ExpiresAt(24小时), Issuer("Signin")
   - 签名密钥：来自 Nacos 配置
4. 返回 token（code=0, message=token字符串）
```

## 四、File 服务（Go gRPC）— 重构核心

### 4.1 小文件上传（流式直传 MinIO）

**流程：**

```
Frontend → /file/upload → OpenResty → Gateway
                                   → file_srv.UploadFile（客户端流式 gRPC）
                                              ↓
                                   io.Pipe（读写管道）
                                   ┌─────────────────────┐
                                   │ pipeWriter ← 数据流 │
                                   │ pipeReader → MinIO  │
                                   └─────────────────────┘
                                              ↓
                                   MinIO.PutObject（同步完成）
                                              ↓
                                   upsertFileAndRelation（事务内写 files/user_files/outbox）
```

**关键代码（file.go）：**

```go
func (s FileServer) UploadFile(stream FileService_UploadFileServer) error {
    // 1. 接收元数据（第一条消息）
    first, _ := stream.Recv()
    meta := first.GetMeta()
    objectKey := buildObjectKey(meta.FileHash)

    // 2. 建立 Pipe：写入端 → MinIO 读取端
    pipeReader, pipeWriter := io.Pipe()
    go func() {
        info, err := internal.MinIOClient.MinIOUploadStream(
            ctx, pipeReader, meta.FileSize, objectKey, meta.ContentType, userMeta)
        uploadResultCh <- uploadObjectResult{info, err}
    }()

    // 3. 接收数据块并写入管道
    for {
        msg, _ := stream.Recv()
        pipeWriter.Write(msg.GetData())
    }
    pipeWriter.Close()

    // 4. 等待 MinIO 上传完成
    uploadResult := <-uploadResultCh

    // 5. 写数据库（事务）
    //    新文件创建时 upsertFileAndRelation 会在事务内：
    //    - 插入 files(status=pending_scan)
    //    - 建立 user_files 关系
    //    - 写 outbox(FILE_SCAN_REQUESTED)
    file, _, _ := upsertFileAndRelation(...)
}
```

**特点：** 文件数据从客户端直接流到 MinIO，服务端只做管道接力和元数据管理。不经过 Kafka，上传即完成。

**InitMultipart（file.go）：**

```go
func (s FileServer) InitMultipart(ctx context.Context, req *InitReq) (*InitResp, error) {
    // 1. 检查是否已存在
    existing, _ := findFileByHash(ctx, req.FileHash)
    if existing != nil {
        // 复用已有对象：
        // success / pending_scan：只补 user_files，不重复投递扫描
        // scan_failed：回到 pending_scan，并重新投递扫描
        file, scanQueued, _ := upsertFileAndRelation(..., existing.Status == model.FileScanFailed)
        return &InitResp{
            ObjectKey: file.ObjectKey,
            Status:    file.Status,
            Message:   reuseMessage(file.Status, scanQueued),
        }, nil
    }

    // 2. 在 MinIO 创建 multipart upload
    ossUploadID, _ := internal.MinIOClient.MinIOMultipartInit(ctx, objectKey, contentType, userMeta)

    // 3. 写入 Redis 元数据（24h TTL）
    internal.RedisClient.HSet(ctx, metaKey(uploadID), map[string]any{
        "user_id": req.UserId, "file_name": req.FileName,
        "file_hash": req.FileHash, "object_key": objectKey,
        "part_size": partSize, "total_parts": totalParts,
        "oss_upload_id": ossUploadID, "status": "init",
    })
    return &InitResp{UploadId: uploadID, PartSize: partSize, TotalParts: totalParts}, nil
}
```

**CompleteMultipart（file.go）：**

```go
func (s FileServer) CompleteMultipart(ctx, req) (*CompleteResp, error) {
    // 1. 从 Redis 读取元数据
    vals := internal.RedisClient.HMGet(ctx, metaKey(req.UploadId), ...)

    // 2. 如果该 upload_id 已经 complete，直接返回当前文件状态
    if statusStr == "completed" {
        return &CompleteResp{ObjectKey: objectKey, Status: currentStatus}, nil
    }

    // 3. 从 MinIO ListParts 获取已上传分片并合并
    parts, _ := listUploadedParts(ctx, objectKey, ossUploadID)
    completeParts := sortByPartNumber(parts)
    info, _ := internal.MinIOClient.MinIOMultipartComplete(ctx, objectKey, ossUploadID, completeParts, ...)

    // 4. 写入数据库
    //    新文件首次落库时，upsert 内部会创建 files(status=pending_scan)
    //    并在同一事务内写 outbox(FILE_SCAN_REQUESTED)
    //    success/pending_scan 复用对象不重复投递
    //    scan_failed 复用对象时由 upsert 内部分支重新入队
    file, _, _ := upsertFileAndRelation(ctx, account, ...,
        fileHash, contentType, objectKey, fileSize, false)
    _ = internal.RedisClient.HSet(ctx, metaKey(req.UploadId), "status", "completed", "etag", info.ETag)
    return &CompleteResp{ObjectKey: objectKey, Status: file.Status}, nil
}
```

### 4.3 文件状态机

```
                                    ┌─ 扫描通过 ─→ status = "success"
status = "pending_scan" ── Kafka ──┼─ 发现病毒 ─→ status = "infected"
FILE_SCAN_REQUESTED 事件             └─ 扫描失败 ─→ status = "scan_failed"

文件上传完成（UploadFile/CompleteMultipart）
  → File.status = "pending_scan"
  → Outbox 写入 FILE_SCAN_REQUESTED 事件 → Kafka
  → store_srv 消费 → Inbox 抢占 → 病毒扫描
  → 更新 File.status = "success"/"infected"/"scan_failed"
```

**当前实现要点：**

- 新对象首次落库时，`upsertFileAndRelation()` 会在事务内创建 `files(status=pending_scan)` 并写 `outbox`。
- 命中已有 `success` / `pending_scan` 对象时，只复用对象并补 `user_files`，不会重复发扫描事件。
- 命中 `scan_failed` 时，`upsertFileAndRelation()` 会把状态重置为 `pending_scan` 并重新投递扫描事件。
- `CompleteMultipart` 支持幂等重放；Redis 中若已标记 `completed`，会直接返回当前文件状态。

### 4.4 文件状态流转与病毒扫描

```
上传完成 → File.status = "pending_scan"
          → Outbox 写入 FILE_SCAN_REQUESTED → Kafka
          → store_srv 消费事件：
              → 先抢占 Inbox 锁，把同一 event_id 收敛为最终只生效一次
              → MinIO 读取对象流 → ClamAV 扫描
              → clean → File.status = "success"（可下载）
              → infected → MinIODeleteObject 删除对象 + File.status = "infected"
              → scan_failed → File.status = "scan_failed"
```

**ClamAV 集成（store_srv/kafka/clamav.go）：**

- 文件上传完成后，store_srv 从 MinIO 读取对象流
- 通过 TCP `host:port` 按 clamd `INSTREAM` 协议把对象流推给 ClamAV daemon
- 扫描结果写入 `files.status` 和 `files.scan_detail`

## 五、Store 服务（Kafka 消费者 / 病毒扫描）

### 5.1 架构说明

重构后，`store_srv` 不再负责 OSS 上传，只消费 `FILE_SCAN_REQUESTED` 元数据事件，执行 ClamAV 病毒扫描。

### 5.2 消费端扫描流程

```go
// store_srv/kafka/kafkacunsumer.go — processMessage 中
// 1. 反序列化 payload，校验 event_type == FILE_SCAN_REQUESTED
// 2. tryBeginInbox(event_id) 抢占 Inbox；DONE 直接跳过，抢不到锁则不提交 offset
// 3. 按 file_id 或 sha1 加载 files 记录；success/infected 直接 mark inbox done
// 4. 从 MinIO 读取对象流，调用 ScanReaderWithClamAV(scanCtx, reader)
// 5. clean  → 更新 files.status=success，清空 scan_detail，写 scanned_at
// 6. infected → 删除对象，更新 files.status=infected，scan_detail=病毒签名
// 7. 失败按 retry/DLQ 流程处理；重试耗尽后标记 files.status=scan_failed
```

### 5.3 消费者配置

```
Broker: localhost:31092
Consumer Group: store_srv_group
Topic: file.upload.cmd
分区策略: Range
自动提交: 关闭
初始偏移: Newest
```

### 5.4 Outbox 模式（FILE_SCAN_REQUESTED）

```go
// enqueueScanRequested — 写入扫描事件
eventID := txID + ":SCAN_REQUESTED"
payload := model.FileEventPayload{
    EventType: model.FileScanRequested,  // "FILE_SCAN_REQUESTED"
    FileID: file.ID, Sha1: file.Sha1,
    OssKey: file.ObjectKey, ContentType: file.ContentType,
}
tx.Create(&model.Outbox{
    EventID: eventID, Topic: model.FileUploadEventTopic,
    Key: file.Sha1, Status: model.OutboxNew,
})
```

> `Key` 使用的是 `file.Sha1` 字段，但当前这个字段承载的是文件内容的 SHA-256 语义哈希，只是名字沿用了历史命名。

### 5.5 Inbox 幂等消费（三阶段获取锁）

```
Phase 1 — 插入新记录：
  INSERT Inbox(event_id, status=PROCESSING, locked_by=instanceID, locked_until=now+2min)
  成功 → 获得锁，开始处理

Phase 2 — 记录已存在：
  查询现有记录
  如果 status=DONE → 跳过（已处理过）

Phase 3 — 锁接管：
  UPDATE Inbox SET status=PROCESSING, locked_by=instanceID
  WHERE event_id=? AND status<>DONE AND (locked_until IS NULL OR locked_until < now)
```

## 六、Email 服务（C++）

### 6.1 架构

```
Kafka Consumer → EmailService 任务队列 → Worker 线程池 → SMTP 发送
                                            ↓
                                     Redis 去重 + 验证码存储
```

### 6.2 核心组件

**Kafka Consumer（librdkafka）：**

- 订阅邮件 topic，自动提交
- 解析邮件地址（处理 %40 URL 编码 → @）
- 入队到 EmailService

**Redis 连接池（hiredis）：**

- 线程安全连接池，默认 8 个连接
- 获取连接时健康检查，失败自动重连

**EmailService（线程池）：**

# 面试问答（模拟面试官提问）

## 架构与设计

### Q1：重构后文件上传和之前最大的区别是什么？

**回答要点：**

- **旧架构**：小文件走 DB+Outbox+Kafka+store_srv（异步，最快也要秒级）；大文件走流式 gRPC 中转（服务端带宽瓶颈）
- **新架构**：小文件用 `io.Pipe` 流式直传 MinIO（同步，毫秒级完成）；大文件用 Presigned URL 浏览器直传 MinIO（零服务端带宽占用）
- **Kafka 角色转变**：不再承载文件上传通道，只负责触发病毒扫描事件

**追问：为什么不用 Kafka 传文件了？**

> Kafka 单消息有大小限制（推荐 < 1MB），大文件不适合序列化到消息体中。且异步处理增加了延迟，文件上传用户期待即时反馈。直接写 MinIO 更简单、更快、更节省服务端资源。

---

### Q2：Presigned URL 上传的原理是什么？安全吗？

**回答要点：**

- 服务端用 MinIO 的 SecretKey 对"目标对象路径 + 有效期 + HTTP 方法"生成签名，生成带签名的 URL
- 前端持该 URL 在有效期内可直接 PUT 文件到 MinIO，无需携带 AccessKey
- **安全措施**：
  1. 签名绑定对象路径和 HTTP 方法，不可跨对象滥用
  2. 有效期短（15 分钟），过期需重新申请
  3. SecretKey 只在服务端持有，前端不暴露
- **对比旧架构优势**：文件数据不经过 Gateway 和 file_srv，节省 100% 服务端带宽

---

### Q3：断点续传是如何实现的？

**回答要点：**

- `InitMultipart` 时将 upload_id、part_size、total_parts 存入 `sessionStorage`（key = 文件 SHA256）
- 再次上传相同文件时，读取缓存的 upload_id
- 调用 `Status` 接口获取已上传分片编号列表
- 只需上传"缺失的分片"，已完成的不重复上传
- MinIO 的 multipart upload 在未 Complete 前会保留已上传的分片

---

### Q4：`io.Pipe` 在流式上传中的作用是什么？

**回答要点：**
为什么要用它？（三大核心好处）在开发后端高性能服务时，io.Pipe 解决的是 “内存占用” 和 “接口不匹配” 的痛点。
A. 零内存积压（Streaming Everything）如果你要处理一个 10GB 的文件并上传：普通做法：读取全量文件到内存 $\rightarrow$ 传输。内存直接 OOM。io.Pipe 做法：一边读、一边传。内存中始终只保留当前正在拷贝的那几十 KB 数据。
B. 完美的接口适配（Glue Code）这是你在 Go 开发中最常用到的。很多 SDK（如 MinIO、AWS S3）的上传接口要求传入一个 io.Reader，而你的数据源（比如计算加密、压缩）往往是产生数据的。使用 io.Pipe，你可以把 PipeReader 塞给 SDK，然后在另一个协程里往 PipeWriter 写数据。它成功地把“写操作”伪装成了“读操作”。
C. 天然的背压控制（Backpressure）由于它是同步阻塞的：如果下游（存储服务器）网络慢，Reader 读取就慢。Reader 慢会导致 Writer 阻塞。Writer 阻塞会反馈到上游，让上游停止读取文件。整个系统会自动达到一种动态的平衡，不会撑爆任何一端的内存。

- `io.Pipe` 创建一对连接：`pipeWriter` 端写入的数据立即被 `pipeReader` 端读取
- goroutine A 接收 gRPC 流数据写入 pipeWriter
- goroutine B 从 pipeReader 读取并传给 MinIO.PutObject
- **优势**：无需将整个文件加载到内存，实现了边收边传的流水线，数据零拷贝（只要 Pipe 内部 buffer 足够）

```go
pipeReader, pipeWriter := io.Pipe()
go func() {
    MinIOClient.MinIOUploadStream(ctx, pipeReader, fileSize, objectKey, ...)
}()
for { pipeWriter.Write(stream.Recv()) }
pipeWriter.Close()
```

### Q5：文件上传后，病毒扫描是如何触发的？

**回答要点：**

1. `UploadFile` 或 `CompleteMultipart` 完成后：
   - 新文件首次落库时，`upsertFileAndRelation()` 会把 `File.status` 置为 `pending_scan`
   - 并在同一个数据库事务里写入 Outbox `FILE_SCAN_REQUESTED`
2. OutboxDispatcher 每 2 秒轮询，发送到 Kafka（topic: `file.upload.cmd`，EventType: `FILE_SCAN_REQUESTED`）
3. store_srv 接收事件，从 MinIO 读取对象流，执行 ClamAV 病毒扫描
4. 扫描完成后更新 `File.status` = `success` / `infected` / `scan_failed`

### Q6：文件下载为什么返回预签名 URL 而不是服务端代理？

**回答要点：**

- **带宽节省**：大文件直接从 OSS 到客户端，不经过 Gateway 和 file_srv
- **延迟降低**：服务端只做签名计算，文件流不走业务网络路径
- **可扩展性**：OSS 天然支持 CDN 加速，预签名 URL 可直接配置 CDN
- **TTL 控制**：当前 10 分钟有效期，过期需重新获取

## 消息队列

### Q7：Kafka 发送是同步还是异步？Ack 级别是什么？

**回答要点：**

- **同步发送**：`SyncProducer`，`SendMessage()` 阻塞直到 Broker 返回 ack
- **Ack 级别**：`WaitForAll`（所有 ISR 副本确认才返回成功）
- **重试**：`Retry.Max = 3`，指数退避（上限 5 分钟）
- **Message Key**：用 `file.Sha1` 字段，同一文件的扫描事件落到同一 Partition，保证有序；当前这个字段实际承载的是 SHA-256 语义哈希

---

### Q8：Outbox 模式现在还用在哪些场景？

**回答要点：**

- 仅用于 **`FILE_SCAN_REQUESTED` 事件**的可靠投递
- 写入 Outbox 和写入 `File` 元数据在**同一个数据库事务**中
- 保证"文件元数据写入 → 扫描事件一定投递"，不会出现"文件在数据库但没人扫描"

```go
db.Transaction(func(tx *gorm.DB) error {
    tx.Create(&file)      // 文件元数据
    tx.Create(&outbox)    // 扫描事件（在同一事务）
    return nil
})
```

### Q9：文件去重的原理？

**回答要点：**

- 上传时计算文件内容哈希作为唯一标识，当前前端实际算的是 **SHA-256**
- `File` 表的 `sha1` 字段有唯一索引，但这是历史字段名，当前承载的是 SHA-256 语义哈希
- 新文件上传时，`findFileByHash()` 返回已存在的 file → 调用 `upsertFileAndRelation` 复用已有 ObjectKey
- 同一文件的多次上传只占用一份 MinIO 存储

### Q15：Go 服务为什么用 `sync.Once` 做单例？

**回答要点：**

```go
var once sync.Once
var jwtInstance *JWT
func GetJWT() *JWT {
    jwtOnce.Do(func() { jwtInstance = &JWT{...} })
    return jwtInstance
}
```

- `sync.Once` 保证初始化函数只执行一次，天然线程安全
- 相比 `init()` 函数的优点：惰性初始化、控制初始化时机
- 相比全局变量的优点：显式控制、初始化失败可 panic、不会重复初始化

### Q17：文件上传和 Kafka 彻底解耦后，如何保证扫描事件不丢失？

- 即使 Dispatcher 崩溃：Outbox 记录状态为 `NEW`，重启后继续扫描未处理的消息
- `FOR UPDATE SKIP LOCKED` 实现多实例安全抢占
- Inbox 幂等消费：同一 EventID 即使重复投递，也只会最终生效一次

### Q18：前端 5MB 阈值的意义是什么？

**回答要点：**

- **小于 5MB**：走流式上传（浏览器先 `arrayBuffer()` 计算 SHA-256，再把原始 `Blob` 作为 body 发到 `/file/upload`）
  - 当前前端为了算哈希，仍会先把整个文件读入内存；5MB 阈值就是把这部分内存成本控制在较低范围
  - 不需要分片逻辑，代码简单
- **大于等于 5MB**：走 Presigned URL 分片上传
  - 避免大文件撑爆内存
  - 支持断点续传
  - 前端并发上传加速

### Q19：ClamAV 病毒扫描是如何集成的？扫描时需要把整个文件下载下来吗？

**回答要点：**

- **不需要完整下载到本地**：ClamAV 支持**流式扫描**，store_srv 从 MinIO 获取对象流（`MinIOGetObjectStream`），再通过 TCP `host:port` 把流推给 clamd 的 `INSTREAM` 协议
- **扫描结果**：clean → `status="success"`；infected → **同时删除 MinIO 中的对象** + `status="infected"`；failed → `status="scan_failed"`
- **为什么删除 infected 文件**：防止病毒文件占用存储空间，同时通知用户重新上传
- **异步执行**：扫描在 file_srv 返回响应后才进行，用户上传完成不等待扫描

### Q21：技术选型依据是什么？

### Q22： 背压怎么做的？

背压控制是怎么做的
“这个项目的小文件上传是流式链路，不是一次性把整个文件读进内存。整体链路是 Browser -> OpenResty -> Drogon Gateway -> Go gRPC file_srv -> MinIO。

背压主要靠两层阻塞自然传递：

OpenResty 侧关闭了请求缓冲，避免先把整个文件落到代理层内存或磁盘。
位置在 nginx.conf

Gateway 侧用 RequestStreamReader 按块读取 HTTP body，再同步写入 gRPC stream。只要下游 writer->Write() 变慢，Gateway 的工作线程就会阻塞，上传速度自然被压下来。
位置在 FileController.cc

Go 服务里又用了 io.Pipe，一边从 gRPC Recv() 拿 chunk，一边把 chunk 写进 pipeWriter；另一边 MinIO 的 PutObject 从 pipeReader 读。io.Pipe 本身是无中间大缓冲的，MinIO 消费慢时，pipeWriter.Write() 会阻塞，这个阻塞会继续传回 gRPC Recv 链路，所以 file_srv 不会无限吞数据。
位置在 file.go (line 688) 和 minio.go (line 107)

所以可以说，这个项目的背压本质上是靠‘流式透传 + 阻塞写 + io.Pipe’形成的自然背压，而不是单独实现了一套复杂的 reactive flow control。

不过如果面试官继续深问，你要主动补一句：当前 Gateway 里的 deque 还是无界队列，这意味着网关层做的是轻量流式中转，但不是最严格的高水位背压。进一步优化可以加 bounded queue 和 high-water mark，超过阈值时暂停读取或直接拒绝请求。”

### Q22： 上传文件失败怎么办？

小文件链路里做了两件关键事：一是错误快速中断，二是失败后尽量清理对象存储副作用。
大文件分片上传这条链路里：

初始化 multipart 之后，会把 upload_id、object_key、part_size、total_parts 等信息放进 Redis。
某几个 part 上传失败，前端不会整文件重来，而是通过 Status 查询已上传 part，再只补传缺失 part。
如果初始化成功但 Redis 元数据写入失败，后端会立刻 AbortMultipartUpload 回滚 MinIO 会话。
CompleteMultipart 时如果发现 part 数量不齐，会直接拒绝合并。
如果业务侧最终落库失败，也会删除已经合并的对象。
用户主动取消或者会话过期时，可以调用 AbortMultipart 中止上传。
这一套的核心目标是：失败时要么能恢复续传，要么能回滚，不让系统留下半完成状态。

### Q23: 文件校验

“这个问题我会分成‘当前已做的校验’和‘还能补强的校验’两层回答。

当前已经做的校验包括：

身份校验
上传前必须先过 JWT，拿到用户身份后才允许进入上传流程。

元数据校验
服务端会校验 user_id、file_name、file_hash、file_size 是否存在且合法，小文件流式上传要求第一帧必须是 meta，大文件初始化也会校验这些字段。
位置在 file.go (line 638) 和 file.go (line 960)

大小校验
小文件流式上传时，服务端会统计实际收到的总字节数 written，最后必须和声明的 file_size 完全一致，否则直接判失败。
位置在 file.go (line 731)

分片合法性校验
大文件上传时会校验 upload_id 是否存在、是否属于当前用户、part_number 是否越界、total_parts 是否匹配；完成合并前还会去 MinIO 列出所有已上传分片，确认数量完整且按 partNumber 排序后才允许 complete。
位置在 file.go (line 1046) 和 file.go (line 1093)

去重校验
前端先算 SHA-256，把 file_hash 传给后端；后端用这个 hash 查文件表，命中则直接复用对象和用户文件关系，实现秒传和严格去重。
位置在 UploadManager.tsx 和 file.go (line 660)

但这里有一个你在面试里最好主动说清楚的点：
当前服务端主要是‘校验前端声明的 hash + 校验实际 size + 校验对象存在性’，还没有在小文件流式上传时再次对整条流做一次服务端 SHA-256 重算。

如果面试官问你‘这样够不够严格’，你可以回答：

对去重和业务流程来说，目前已经能工作；
但如果要做到更强的防篡改校验，我会在 Go 侧上传时用 io.TeeReader 或 hash.Hash 一边透传到 MinIO，一边实时计算服务端 SHA-256，上传完成后把服务端计算结果和前端声明的 file_hash 做最终比对；
这样不需要额外再读一遍文件，也不会明显增加内存占用。
