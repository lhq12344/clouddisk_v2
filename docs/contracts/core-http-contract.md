# Core HTTP Contract Snapshot

Date: 2026-09-05

Source of truth for this snapshot: `forward_part/static/services/api.ts`, `forward_part/gateway/controllers/AccountController.h`, and `forward_part/gateway/controllers/FileController.h`.

The migration keeps these paths, methods, authentication requirements, request fields, and key response fields compatible with the current frontend. The frontend has now intentionally moved small uploads onto the multipart presigned flow; `/file/upload` and `/file/uploadpart` remain only as authenticated fail-closed compatibility routes.

## Shared Behavior

- `ApiService.request()` attaches `Authorization: Bearer <token>` when `localStorage.oss_token` exists.
- JSON request bodies receive `Content-Type: application/json` automatically.
- Every API request receives an `X-Request-Id` header generated by the frontend.
- Non-2xx responses are surfaced to the frontend as `[STATUS_<code>]: <message>` using `message`, `details`, or raw response text.

## Account Endpoints

| Use case | Method | Path | Auth | Request fields | Success response used by frontend | Compatibility notes |
|---|---:|---|---|---|---|---|
| Signup | POST | `/user/signup` | No | `username`, `password`, `email` | Any 2xx JSON/body accepted | Starts pending registration; account creation must happen after verification-code success. |
| Signin | POST | `/user/signin` | No | `username`, `password` | `token` | Token is persisted to `localStorage.oss_token`; JWT must keep `issuer=Signin`, `ID`, and `Name` claims compatible. |
| Send verification code | POST | `/user/sendcode` | No | `email` | Any 2xx JSON/body accepted | Core queues an `EMAIL_VERIFICATION_REQUESTED` outbox command so email delivery is retryable. |
| Verify code | POST | `/user/code` | No | `email`, `code` | Any 2xx JSON/body accepted | Target contract: consume pending registration and create account atomically; duplicate success must not create duplicate account. |
| User info | GET | `/user/info` | Yes | None | User info JSON returned by gateway | Uses authenticated request context, not client-provided identity. |
| Logout blacklist | POST | `/user/token/blacklist` | Yes | `token` | Any 2xx JSON/body accepted | Used by frontend logout before clearing token and multipart sessions. |
| Token whitelist | POST | `/user/token/whitelist` | Yes | `token` | Any 2xx JSON/body accepted | Existing route remains until JWT lifecycle is fully owned by Core API. |

## File Metadata and Access Endpoints

| Use case | Method | Path | Auth | Request fields | Success response used by frontend | Compatibility notes |
|---|---:|---|---|---|---|---|
| Query files | POST | `/file/query` | Yes | None | `filelist[]` with file name/hash/size/status fields | Must query MySQL only; object storage calls per listed file are forbidden. |
| Download URL | POST | `/file/download` | Yes | `filename`, `filehash`, `file_size` | `download_url` | Core API authorizes owner and scan status before requesting presigned GET. |
| Preview URL | POST | `/file/showfile` | Yes | `filename`, `filehash`, `file_size` | URL/message field accepted by existing UI path | Same authorization and scan-state rules as download. |
| Delete file | POST | `/file/delete` | Yes | `filename`, `filehash` | status/code message | HTTP transaction removes user relation and emits cleanup event if last reference. |
| Small upload removed | POST | `/file/upload` | Yes | Deprecated headers/body ignored | Error JSON | Compatibility route retained only to fail closed; current frontend has no active `/file/upload` call. |

## Multipart Upload Endpoints

| Use case | Method | Path | Auth | Request fields | Success response used by frontend | Compatibility notes |
|---|---:|---|---|---|---|---|
| Init multipart | POST | `/file/initupload` | Yes | `file_name`, `file_hash`, `file_size`, `content_type` | `upload_id`, `object_key`, `part_size`, `total_parts`, `status`, `message` | Creates durable upload session in target design; Redis may cache but is not source of truth. |
| Presign parts | POST | `/file/PresignParts` | Yes | `upload_id`, `part_numbers[]` | `upload_id`, `parts[].part_number`, `parts[].url`, `parts[].expires_at` | User must own upload session; Storage Control does not decide ownership. |
| Loopback part proxy removed | POST | `/file/uploadpart` | Yes | Deprecated header/body ignored | Error JSON | Compatibility route retained only to fail closed; frontend now PUTs directly to presigned URLs. |
| Complete multipart | POST | `/file/CompleteMultipart` | Yes | `upload_id` | `upload_id`, `object_key`, `etag`, `status` | Metadata, relation, and scan outbox write must commit atomically after storage complete. |
| Abort multipart | POST | `/file/AbortMultipart` | Yes | `upload_id` | Empty/JSON response accepted | User must own session; operation is idempotent. |
| Multipart status | POST | `/file/Status` | Yes | `upload_id` | `total_parts`, `uploaded_parts[]` | User must own session; supports resume after Core API restart. |

## Error Mapping To Preserve

- Missing or invalid JSON remains `400`.
- Missing/invalid JWT remains `401`.
- Downstream or storage unavailability maps to retriable 5xx or explicit unavailable status.
- File unavailable because of scan state or infection remains a non-2xx conflict-style response to prevent download/preview.

## Defect Fixed By Core Path

The old `/user/code` gateway path verified only the Redis code. The Core path intentionally fixes this: verification atomically creates the account from pending registration data and treats already-created accounts idempotently.
